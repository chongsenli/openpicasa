### M4-BUG-01 方格显示文件名开关失效（阻塞项）

**现状（代码事实）**：`topbar.rs:721` 在「更多」菜单里发出 `MoreAction::ToggleShowFilename`；`draw_overlays` 的 `for a in actions` 分支（`app.rs:2234-2256`）未处理该动作，落入 `_ => {}` 被丢弃；唯一翻转 `self.grid_show_filename` 的代码在 `app.rs:1753-1755`，位于 `topbar::show()` 的输出分支，而该处只发 `ToggleMoreMenu`，属**不可达死代码**。报告 §4 已用「同一交互点『全屏』可生效」排除坐标/驱动因素。

**怎么改**：

1. 在 `app.rs:2234-2256` 的菜单动作 `match` 中显式处理 `MoreAction::ToggleShowFilename`，翻转 `grid_show_filename`；或把菜单动作统一回流到 `app.rs:1753-1755` 的翻转逻辑。**二选一，不许两处都写**（双写会造成二次翻转）。
2. 删除 `topbar.rs::show()` 输出分支里的死代码，或在注释中明确标注「菜单动作不在本分支消费，见 `draw_overlays`」，避免后续再被误当成有效实现。
3. 开关状态沿用现状：会话级即可（`09` §2 记录为绘制层开关）；本版不新增持久化要求。
4. 顺带核对「更多」菜单其余动作（`AddFolder` / `ToggleRecurse` / `ToggleFullscreen` / `About` / `ToggleShowFilename`）在 `draw_overlays` 中**逐项有分支**，补一条枚举穷尽匹配或编译期守卫，防止再次漏接。

### M4-BUG-02 toast 恒被丢弃（本版反馈链路前置）

**现状（代码事实）**：`lib.toast: Option<(String, f64)>` 的第二个元素是**持续秒数**（`library.rs:172`，各调用点传 `3.0` / `2.5` / `6.0`）；渲染时 `app.rs:2669` 用 `remaining = ttl - now`，而 `now = ctx.input(|i| i.time)` 是**自启动累计秒数**，导致启动 3 秒后 `remaining` 恒为负，toast 被立即清空（`app.rs:2670-2675`）。报告 §6 已记录该现象，因 toast 全套属「未宣称/未测」故未判 FAIL。

**为什么本版必须修**：§2 要求导入、导出提供明确的**成功 / 失败 / 取消**状态反馈，toast 是最轻量的落点（M32-UI-10 的 `已加入托盘` 也依赖它）。带着一个永不显示的 toast 去做进度反馈，等于把「失败不静默」（R-M2-4）架在坏链路上。

**怎么改**：

1. 把 toast 的语义从「持续时间」改为「**到期时刻**」：写入时存 `now + ttl`（绝对时间），渲染时 `remaining = expires_at - now`；或保留持续时间但增记 `created_at`，两处时间口径必须同为 `ctx.input(|i| i.time)`。
2. 统一所有 `toast = Some((msg, n))` 调用点的含义，不改动各条文案与时长（约 20 处，`app.rs` 与 `library.rs`）。
3. 查看器打开时仍不画 toast（现状 `app.rs:2670` 的沉浸式规则保留）；退出查看器后未过期的提示应能继续显示。
4. 补一条单测：模拟 `now = 0` 与 `now = 启动后 600 s` 两种时刻，toast 都在 `ttl` 秒后消失，且不提前消失。

**验收标准**：

- [ ] 应用启动 10 分钟后触发任一 toast（如「已放入托盘 3 张」），提示可见并按时长自行消失。
- [ ] 导入 / 导出成功、失败、取消三种结果各自产生一条可见 toast，文案与操作状态区一致（§2.1）。
- [ ] 查看器内不弹 toast；退出后未过期提示仍可见。

### M4-BUG-03 tooltip 快捷键格式统一

## 2. 索引管理与导入导出（新增核心，M4-IDX）

### 2.0 术语与范围

| 术语 | 定义 |
| --- | --- |
| **索引记录** | 应用自有数据库中的派生数据：`roots` / `folders` / `photos` / `thumbs` 元数据 / `settings` / 任务与失败记录 / 排除项。可随时删掉重扫重建 |

| **图库路径信息** | 图库根目录路径、`path_key`、卷大小写规则、文件夹相对路径，以及离线/关闭状态 |

### 2.1 索引管理窗口优化（M4-IDX-01～06）

**现状（代码事实）**：非模态窗口 + 四标签，`MgmtSnapshot` 单一数据源（`index_mgr.rs:246-320`、`mgmt.rs:313-360`）；没有「总览」层，用户要自己翻四个标签才能拼出「我的库现在怎么样」；`Confirm` 二次确认已有（`index_mgr.rs:77-120`），但仅覆盖全量重建/删除索引等既有危险动作。

**怎么改**：

1. 在标签栏**之上**增加常驻「总览摘要区」（不随标签切换消失），按 §2.1.1 字段表展示；四个既有标签**保留不重命名**（`MgmtTab::ALL` 仍是 4 项，`mgmt.rs:288-301`），另在标签栏新增**第五个标签「导入 / 导出」**承载本版新操作（或经 §7 P-M4-05 裁决后改为总览区内的操作卡片；默认按新增标签实现）。
2. 操作状态区（进度 / 成功 / 失败 / 取消）为「导入 / 导出」标签内的常驻区域，见 §2.1.2。

#### 2.1.1 总览摘要字段口径（M4-IDX-01～02）

### 2.2 索引文件 / 索引包格式与版本（M4-IDX-10～14）

> 本节兑现验收重点「能识别索引文件版本，并对不兼容情况给出明确提示」与「定义索引文件的版本信息及升级策略」。

#### 2.2.1 格式定义（M4-IDX-10）

**默认方案**（§7 P-M4-05 待确认，dev 不得自行改）：

| 形态 | 扩展名 | 内容 | 何时产出 |
| --- | --- | --- | --- |
| **索引文件** | `.opicasaidx` | 单个 SQLite 数据库文件；SQLite `application_id` 写入本格式 magic；库内含 `index_manifest` 清单表 + 导出的数据表 | 默认导出 |
| **索引包** | `.opicasaidx.zip` | ZIP：上述索引文件 + 可选 `thumbs/`（缩略图按 `photo_id` 命名）+ `checksums.sha256` | 用户勾选「包含缩略图」时 |

选 SQLite 作载荷的理由：与现有 `picasa-db` 同构，**事务 / 原子提交 / 迁移框架 / 单写者可直接复用**，不需要新引一套序列化与校验代码；ZIP 包只解决「附带缩略图」这一可选项。

**`index_manifest` 清单表字段**（导入前、导出后都必须可读）：

| 字段 | 类型 / 取值 | 用途 |
| --- | --- | --- |
| `format_version` | INTEGER，本版 = **1** | 索引文件**格式**版本（独立于 DB `schema_version`） |
| `min_reader_version` | TEXT，应用版本 | 能读该文件的最低 OpenPicasa 版本；高于当前版本即拒绝 |
| `app_version` | TEXT | 生成该文件的 `env!("CARGO_PKG_VERSION")` |
| `schema_version` | INTEGER | 导出时 DB 迁移版本（当前 7，本版升 8，见 §3.2/§5.1） |
| `created_at` | INTEGER（Unix 秒） | 生成时间 |
| `content_flags` | TEXT（JSON） | `index_records` / `user_data` / `paths` / `thumbnails` 四项布尔 |
| `counts` | TEXT（JSON） | `photos` / `roots` / `folders` / `tags` / `albums` / `thumbs` 数量，供导入预览与结果核对 |
| `source_roots` | TEXT（JSON） | 每个根：`path` / `path_key` / `case_insensitive` / `state` / `is_online` |
| `payload_checksum` | TEXT | 对全部数据表内容计算的 SHA-256（校验和不计入自身） |
| `notes` | TEXT | 生成时的备注（如「含 3 个离线根」），可为空 |

#### 2.2.2 版本识别与升级策略（M4-IDX-11～12）

| 文件侧版本 vs 当前应用 | 行为 | 用户提示 |
| --- | --- | --- |
| `format_version` 或 `schema_version` **高于**当前支持值，或 `min_reader_version` > 当前应用版本 | **拒绝导入**，现有索引零改动 | 「该索引文件由更新版本的 OpenPicasa（x.y.z，格式 vN）生成，请升级应用后重试」 |
| 同 `format_version`、`schema_version` **低于**当前值 | 在**临时 staging 库**上按 `MIGRATIONS` 顺序升级到当前 `SCHEMA_VERSION`，再进入导入预览；**原文件只读不改** | 「检测到旧版索引（vN），将在导入时自动升级」 |
| 同版本 | 直接进入导入预览 | — |
| `format_version` 为 0 / 缺 manifest / magic 不符 | 拒绝 | 「不是 OpenPicasa 索引文件」 |
| `payload_checksum` 不符 / 必需表缺失 / SQLite 打开失败 | 拒绝 | 「索引文件已损坏（校验和不匹配 / 缺少数据表），现有索引未改动」 |
| `format_version` **未来值**但 `min_reader_version` ≤ 当前 | 按未知扩展字段**跳过并计数**，不猜语义；在导入预览列出「跳过的未知字段 N 项」 | 明确提示可能丢信息，需用户确认 |

- 升级只在 staging 库发生，**失败即删 staging**，现有索引保持可用（R-M4-2）。
- 拒绝降级：`schema_version` 高于当前时不得「试着读一读」，与 `05` §5 第 2 条 `SchemaTooNew` 守卫一致。
- **格式版本一旦发布不得复用**：format v1 的字段只增不删；删字段必须升 v2。此规则写入 ADR（§10 下游文档）。

#### 2.2.3 内容默认（M4-IDX-13）

| --- | --- | --- |

| 用户数据（星标 / 说明 / 标签 / 相册及成员） | **包含** | §7 P-M4-01 建议；使换机/恢复后整理关系不丢 |

#### 2.4.3 事务与临时文件（实现约束，兑现 `M4-IDX-36`）

1. **staging 阶段**：把索引文件复制到应用临时目录（**不在照片目录内**），在 staging 库上完成版本升级、完整性校验、内容解析、冲突计算；此阶段**完全不碰现有库**。
2. **提交阶段**：对现有库用 `VACUUM INTO` 生成一份备份（`05` §4.5 同款），随后在**单个 SQLite 事务**内完成合并/替换写入；事务提交成功才删除 staging 与备份（或按保留策略留备份供恢复）。
3. **失败 / 取消 / 强杀**：事务未提交即回滚；staging 与临时文件在下次启动时按标记清理；**现有库始终是可用的完整版本**。
4. 导入与后台扫描/索引任务**串行化**：导入提交期间暂停索引任务（复用 M2 的暂停态与任务调度），避免双写者竞争；恢复后增量核对，不重扫全库。

#### 2.4.4 合并 / 替换 策略与冲突规则（默认，细则见 §7 P-M4-03）

**身份键**：优先 `(root_path_key, 文件夹相对路径, name_key)`；路径不匹配时退到 `(size_bytes, mtime_ns, head_hash)`（头部哈希 M3 已入库，`08` §二），再退到 `(name, size_bytes)` 并标记为「低置信匹配」需用户复核。

| 场景 | 合并（默认） | 替换 |
| --- | --- | --- |
| 仅导入文件有 | 新增记录（计入成功导入），照片标记「路径待匹配 / 离线」 | 写入 |
| 双方身份相同、内容一致 | 跳过（计入跳过），保留现有 | 以导入为准 |
| 双方身份相同、内容不同（size/mtime/EXIF 不一致） | **保留现有**（默认），计入冲突并列入结果清单；不静默覆盖 | 以导入为准，冲突数计入结果 |
| 仅现有库有 | **一律保留，绝不删除** | **删除**（现有独有的标签/相册/说明丢失，须二次确认列数量） |
| 标签 / 相册 / 说明 | 按名称合并、关系按身份键并入并去重；同名不重复创建 | 整体替换为导入内容 |
| 图库根目录 | 合并：追加新根（路径冲突时提示重映射），不动现有根 | 整体替换；导入后统一进入「重新匹配」流程 |
| 备份 | 不需要（现有数据不丢） | **必须先备份成功**，否则禁止替换 |

- 「合并」的硬约束：**不删除任何现有记录、不修改现有照片文件**；任何「会丢数据」的行为只能属于替换策略且必须二次确认。
- 导入结果报告中的「失败」指单条记录写入失败（如约束冲突），不是整体失败；整体失败时报告显示「导入失败，现有索引未改动」。

#### 2.4.5 取消语义

| 取消时点 | 行为 | 状态 |
| --- | --- | --- |
| 校验 / staging 阶段 | 删除 staging，现有库零变化 | 「已取消 · 现有索引未改动」 |
| 提交事务执行中 | 事务回滚（SQLite 单事务原子） | 同上 |
| 提交已完成后点取消 | 按钮置灰 / 不响应（已无取消语义） | 显示成功结果 |

#### 2.4.7 重新匹配图库根目录

- 导入完成后，若 `source_roots` 中任一路径在本机不存在或与现有 `roots.path_key` 不符，提供「重新匹配图库根目录」：逐根选择本机目录，或按 `path_key` 自动给出候选并确认。
- 映射生效后：更新 `roots.path` / `folders.path` 的对应关系，**复用 M3 的 L1（目录 mtime 快筛）+ L2（文件级全校）增量核对**（`08` §1.1），不复制、不移动、不重命名任何照片文件。
- 未匹配 / 仍不存在的根：其照片保留索引记录，标记**离线**（`folders.is_online = 0` / `roots.state`），缩略图与整理关系保留；用户可稍后再匹配（对应 `01` F1-06「盘符变化重映射」的本版最小实现）。
- 重新匹配是**可选后续动作**，不阻塞导入结果查看；关闭窗口后再次进入仍可继续。

- 沿用大图库分页：拍摄时间排序走键集分页；**补齐其余排序所需索引**（`idx_photos_size_id` 等，`07` §5.2 / `08` §四登记为 M4 事项），组合筛选不得退化为全表扫描。

## 9. 全局门禁与风险

### 9.1 全局门禁（沿用，不回退）

- `cargo check --workspace` / `cargo clippy --workspace --all-targets -D warnings` / `cargo test --workspace` 全绿（除已登记的容器环境预存失败项）。
- **照片目录零写入**：`TC-RO-001` 全流程复跑；不读写 `.picasa.ini`（D-18）。

- **备份与恢复**：标签、相册、星标、说明、近期搜索、索引记录纳入迁移 / 备份 / 恢复测试（验收重点 7）。

- **索引文件**：5 类坏文件 + 高/低版本 + 强杀中断用例全覆盖。

### 13.7 性能回归修复：索引与缩略图展示变慢（2026-11-06，用户反馈）

   `UPDATE` 事务提交**，还用 `request_repaint_after(200ms)` 强制持续重绘。

2. **左栏每帧查库**。`sidebar::m4_group` 每帧调 `all_tags()`（全表 `GROUP BY`）+
   `all_albums()`（带相关子查询计数），绘制帧重复跑。

| 层 | 改动 |

### 13.8 索引变慢 + 程序崩溃（2026-11-06，用户复测反馈）

**现象**：「索引速度太慢，而且还有程序崩溃行为」；此前还观察到
`epaint::mesh::append_ref` 的 `Other mesh is invalid` debug 断言 panic（exit 101）。

**根因（一）索引慢 —— EXIF 后台线程持锁做文件 I/O**：

§13.7 把回填移到了后台线程，但**仍在 `Mutex<Db>` 锁内**调用 `backfill_batch()`，
而该函数逐张 `picasa_imaging::probe()`（`File::open` + 解析 EXIF）。磁盘 I/O 期间
索引 / 缩略图写入线程全部被堵 —— 比原来 UI 线程版本更隐蔽，表现仍是「索引太慢」。

**修复**：`m4_exif.rs` 拆成三段，锁只在 ①/③ 出现（各毫秒级）：

```text
① collect_pending(db, 20)  持短锁：取 (id, abs_path)，立刻放锁
② probe_paths(pending)     完全无锁：最贵的 File::open + EXIF 解析
③ write_batch(db, items)   持短锁：单事务批量写回，立刻放锁
```

`app.rs::tick_m4_exif` 的后台线程改用这三段；两段持锁都用 `try_lock` 40×25ms 退避，
拿不到锁就放弃本批、下帧重试，绝不阻塞。
新增 `crates/picasa-core/tests/m4_exif_lock.rs`（2 条）：**探测阶段另一线程反复拿锁
写入，单次等锁 < 250ms**，直接证明索引/缩略图线程不再被堵；另一条验证三段与
`backfill_batch()` 等价。

**根因（二）崩溃 —— debug 构建下退化几何触发 epaint `debug_assert`**：

`epaint 0.37 mesh.rs:148` 的 `debug_assert!(other.is_valid(), "Other mesh is invalid")`
在合并 Mesh 时校验「索引 < 顶点数」。窗口最小化 / 尺寸变化 / 侧栏收起过渡帧里，
`viewport_rect()` 或 `allocate_exact_size` 可能给出宽度 0 / 负 / 非有限的 rect，
tessellate 后产生索引越界的 Mesh → debug 下直接 panic。短跑（8/12/20/25 秒）均无法
复现，因为需要 GUI 交互触发的窗口状态变化。

**修复（防御 + 规避双管）**：

| 层 | 改动 |
| --- | --- |
| `app.rs` toast 绘制 | 画之前校验 `viewport_rect()`：宽 ≥ toast 宽+8、高 ≥ toast 高+56、`is_finite()`，不满足就跳过这一帧（视口恢复后自然重画） |
| `sidebar.rs` `m4_group` | 组头与每一行 `allocate_exact_size` 前 `available_width().max(1.0)`，绘制前校验 `rect.width() >= 2.0 && is_finite()`，退化即跳过，避免无效 Mesh |
| `run-isolated.sh` | **默认改用 `target/release/OpenPicasa`**：① 性能（debug 下 EXIF/缩略图路径明显慢，易被误判为「索引变慢」）；② `Other mesh is invalid` 是 `debug_assert`，release 下被编译掉。`--debug` 可切回 |
| release 二进制 | 已 `cargo build --release --bin OpenPicasa`，实测二进制不含该断言字符串，短跑 10 秒零 WARN/ERROR/panic |

**验证**：`cargo check` ✅ / `clippy -D warnings` ✅ / `cargo test --workspace` **489 条全绿** ✅
（`m4_exif_lock` 2 条）；`bash -n run-isolated.sh` ✅；release 短跑 10 秒日志干净。
真实用户库仍为 v7、未被改动。

需要 `RUST_BACKTRACE=full` 在复现场景抓栈）。当前是「几何防御 + release 规避 + debug 断言不触发」
三层保险，**未宣称定位到具体那一个 Shape**。此外用户提到的「点击导入图片没有预览图」是
F1-07 导入向导（选前缩略图预览）未实装，属独立功能缺口，不在本轮修复范围。
