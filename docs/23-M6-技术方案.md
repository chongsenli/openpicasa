## 2. 主图长边 2560 与「真 100%」：内存 / GPU 与建议口径

### 现行上限（两套数字，不要混用）

1. **实际上传到 GPU、也用于 100% 缩放基准的纹理**：UI 在收到原图 RGBA 后立刻 `resize_to_fit(&img, 2560)`。主图与并排比较图都是这条路径。

```2314:2321:crates/picasa-ui/src/app.rs
                            // 上传前缩到 2560：一张 24MP 的 RGBA 纹理是 96MB 显存，
                            // 而我们最多看到 8 倍缩放，2560 长边足够（M1 取舍，见实施说明）。
                            let small = picasa_imaging::resize_to_fit(&img, 2560);
```

2. **文档 / API 里的 T1**：`picasa-imaging` 的 `THUMB_T1 = 2048`，注释写「查看器适应窗口用它，100% 时才回源解码原图」。`ThumbService::viewer_max_edge()` 也返回 `THUMB_T1`。**但 `JobKind::Viewer` 的实际实现并没有缩到 2048**，而是 `decode_oriented(&job.path)` 解出**整张摆正后的原图像素**，再经 `FullImageReady { w, h, rgba }` 把完整 RGBA 送到 UI 线程，由 UI 再缩到 2560。`THUMB_T1` 在这条热路径上基本是过时注释。

3. **解码守门**：`DECODE_MAX_PIXELS = 80_000_000`（80 MP），`DECODE_MEM_CAP_MB = 512`。超过 80 MP 在进解码器前直接拒绝。注释写这是折中，100 MP TIFF 的内存门禁「P-32 仍待定」。

4. **「100%」的语义**：`Viewer::zoom_actual()` 把 `zoom = 1.0`，绘制尺寸是 `tex_size * zoom`。`tex_size` 是**降采样后的纹理**，不是原图像素。因此当前「100%」= 长边最多 2560 的纹理按 1:1 显示。把缩放推到 `ZOOM_MAX = 8.0` 也只是把这张 2560 图放大，**不会出现更多原图像素**。这与「选片检焦看真 100%」不是同一口径。

### 调用链与峰值内存

```
翻页 / 打开
  → viewer::ensure_loaded()        // UI 线程：只排队，不解码主图
  → ThumbService::request(JobKind::Viewer)
       后台 4 线程（THUMB_WORKERS）
       → decode_oriented(path)
            std::fs::read 整文件
            → decode_bytes（JPEG/PNG/… 或 heic / rawler）
            → 按 EXIF 摆正，得到满幅 RGBA
       → 经 mpsc 发送 FullImageReady { rgba: img.into_raw() }
  → OpenPicasaApp::pump_events     // UI 线程
       从 raw buffer 再拼 RgbaImage
       → resize_to_fit(..., 2560)
       → ColorImage + ctx.load_texture(...)
       → 直方图在 2560 图上计算（再采样到 512²）
```

粗算峰值（单张、未计文件字节与其它缓存）：

| 原图 | 解码后 RGBA | 再加通道里的一份拷贝 | 2560 纹理（约） |
| --- | --- | --- | --- |
| 24 MP | ≈ 96 MB | 峰值可能到 ≈ 192 MB（worker 出图 + 通道/UI 重组） | 长边 2560 的 RGBA，约十几 MB 量级 |
| 80 MP（上限） | ≈ 320 MB | 峰值可能到 ≈ 640 MB，已贴近 / 超过 `DECODE_MEM_CAP_MB = 512` 的设计意图 | 仍缩到 2560 |

还有：比较图走同一通道、同一套满幅解码；快速连翻时过期任务**不会取消**（见第 3 问），多张满幅 RGBA 可能同时存在于 4 个 worker 里。GPU 侧当前只常驻 2560 纹理，显存风险低于 CPU 内存；真 100% 上传原图后，GPU 与 CPU 会一起涨。

T0 预览（512）已用于「大图未到时顶上」，本身不是 2560 问题的解，只减少黑帧。

### 建议（技术建议，不是产品决定）

1. **先让产品拍板「真 100%」口径**，再谈实现：
   - A. 检焦需要原图像素 1:1（推荐对「选片」承诺）；
   - B. 继续允许降采样，但必须在 UI / 说明书写清「超过 N 仍降采样」，不要再把按钮叫成容易误解的「100%」。
2. **不要**把「解完整张 80–100 MP RGBA，再整幅上传 GPU」当作默认路径。24 MP 已经是 96 MB 级；100 MP 是 400 MB RGBA，再加上拷贝与 8× 缩放，内存和上传都很容易打穿笔记本。
3. 若选 A，建议组合而不是单打一：
   - **按需原图像素**：适合窗口 / 胶片条继续用已有 T0（512）+ 至多 2560（或真正启用 T1=2048）的预览链；只有用户进入 100% 或放大超过预览分辨率时，才对**可见区域**解码更高分辨率。
   - **图块 / 视口解码**：JPEG 可走已有 `decode_jpeg_scaled`（DCT 1/8、1/4、1/2）再按视口补全；其它格式要逐个评估。整幅 100 MP 纹理上传不建议作为 M6 默认。
   - **仍设硬顶**：保留并产品化「超过 N MP 仍降采样 / 拒绝」。现行 80 MP 是解码拒绝线，不是「显示 100%」的线。建议把「显示用上限」和「解码拒绝上限」分开写。N 需要压力测试后才能定；本轮**没有** 100 MP 实测，不能替 P-32 拍板。
4. 粗估 / 非承诺：只改文案与按钮语义（口径 B）：**0.5–1 天**。真正做按需 / 分块 100%（口径 A，先 JPEG）：**1–2 周**；再加上 HEIC/RAW/TIFF 分块与 50–100 MP 压力门禁：**2–4 周**，且强依赖测试机与样张。风险：把满幅原图直接上传看起来快，但会在大图上把内存打爆。

## 3. 连续翻页（无黑帧 / 预加载 / 过期取消）与信息栏 EXIF

### 3.1 查看器主图：异步解码原图，但翻页会拆掉当前纹理

- 主图解码在 `ThumbService` 后台线程，**不**在 UI 线程同步解主图。
- 一旦翻页，`Viewer::jump_to()` 会立刻把 `tex` / `preview` / `loaded_id` / `requested_id` / `compare_tex` / `exif` 全部清空，注释写明是为了「避免上一张残影」。在新 T0 或 2560 到达前，主画布只剩背景 +「正在解码…」。若栅格缓存里已有该张 T0，同一帧可以用 512 顶上，并显示「正在载入原图…」。
- **没有「下一张主图预加载」**。`JobKind::Viewer` 只为**当前张**以及比较模式的**右侧下一张**排队。连翻时不会提前解 n+1 / n-2。
- **没有过期取消**。`ThumbService::request` 只用 `inflight: HashSet<(photo_id, kind)>` 去重；任务一旦 spawn，就会跑完并发送事件。UI 只在 `pump_events` 里丢弃 `requested_id` 不匹配的 `FullImageReady`。连翻会在 4 个 worker 上堆满幅原图解码（24 MP 注释为 200–400 ms），过期结果白做，还可能堵住后面真正要用的那张。
- 与比较图**共用同一条** `JobKind::Viewer` 通道。快速切页时，比较图请求更容易和主图抢 worker。比较右图始终 `fit_rect` 适配窗格，**不**跟随左侧 `zoom` / `pan`（这是 M5 已定的「只并排、不同步」；若 M6 升级同步，是加法，不是现成开关）。

差在哪（相对「无黑帧、预加载、过期取消」）：

1. 翻页先清空再等，而不是保留上一张直到下一张就绪（或先切到已预载的纹理）。
2. 没有下一张 / 上一张的有界预载队列。
3. 没有取消令牌；过期只在应用层丢事件。
4. 每次查看器任务都是满幅 `decode_oriented`，成本远高于「先 T1 / 先屏幕分辨率」。
5. 同一次 `ensure_loaded` 还在 UI 线程**同步 probe 原图 EXIF**（见下），连翻时会叠加主线程卡顿。

### 3.2 信息栏 EXIF：现行仍同步读原图；库里其实已有大半字段

`viewer::ensure_loaded` 注释写「EXIF 只读探测：……同步做即可（换页手感更稳）」：

```534:547:crates/picasa-ui/src/viewer.rs
        return;
    }
    viewer.requested_id = Some(row.id);
    service.request(ThumbJob { ... kind: JobKind::Viewer });
    match picasa_imaging::probe(&row.abs_path()) {
```

- `picasa_imaging::probe` 打开原文件读 EXIF（`kamadak-exif`）。照片不在本地（离线 / 云端占位）时，信息栏会走失败分支（「元数据读取失败」），即使索引库里可能已有回填结果。
- 与此同时，**索引库已有 EXIF 列**（v8 起，现行 schema v9 仍保留）：`camera_make` / `camera_model` / `lens_model` / `focal_length` / `f_number` / `exposure_time` / `iso` / `exif_status` / `exif_error`，并有 `Db::photo_exif` / `set_photo_exif_batch`。后台 `tick_m4_exif` 已在 UI 帧外分批 `probe_paths` + 写库。`PhotoRow` 本身带 `width/height/orientation/taken_at/taken_at_src`，但**不含**相机 / 镜头 / 曝光字段；查看器也没有去读 `photo_exif`。
- 相对 `ExifSummary`，库里**没有** `color_space`、`gps`（以及独立的 `taken_at_text`；拍摄时间可用行上的 `taken_at`）。若改读库，这两项要么降级为「—」，要么先扩列（那是 schema 变更，不建议塞进翻页热修）。

结论：**现行查看器信息栏仍同步读原图，不是读索引库。** 离线仍显示——以现在的代码——**做不到**（除非碰巧 probe 还能打开文件）。改读索引库与「翻页预加载 / 取消」适合放在同一个技术包：二者都要改 `ensure_loaded` 与查看器的请求生命周期，而且同步 probe 本身就是连翻卡顿的一部分。建议顺序：先切到「库内字段（缺的再显示 —，不要阻塞）」→ 再加预加载与取消 → 最后才考虑要不要在空闲时补 probe。不要反过来先做满幅预加载却把同步 EXIF 留在主线程。

粗估 / 非承诺：EXIF 改读库（含离线回退与缺列口径）：**1–2 天**。翻页预加载（±1 张、有界、T1 或 2560，而不是再堆满幅 80 MP）+ 过期取消 + 避免先清纹理导致的黑帧：**3–7 天**。若与真 100% 分块绑在一起做：**再加 1–2 周**。上推：无取消原语要先给 `ThumbService` 加 generation / token；比较通道要分流。下推：只做「保留 T0 直到大图到达 + 丢弃过期 + EXIF 读库」，不做分块。

本轮**没有**在约定机上测冷启动到首张可交互、或连续翻页黑帧时长。早期 F10 红线（如 10 万张冷启动 ≤5 s、24 MP 首帧 &lt;200 ms）在现行 M5 通过条件里**不存在**，也不能用网格 DB 毫秒数代替。若 M6 要设门禁，需先约定测试机、图库与指标，再测一条基线。

### 4.1 r8 已落地、以及仍不能说的话

已落地（`dba6749` / `9ce3b58`，现行树未回退）：

### 4.2 确认框之外，更值得看的点

按「性价比 / 不回退 r8 边界」排序：

1. **查看器翻页管线**（第 3 问）——对「选片手感」影响最大，也是产品希望 M6 先讨论的 P0。建议作为 M6 技术包的主项。
2. **确认框仍每帧构造 / 比较完整选择集**——大选集（上千张）上，`selection_ids` + `TrashScope::new`（再排序去重）+ `matches` 仍是 O(选中数)／帧。不需要、也不应该改「最多 3 条预览、完整执行集合」。下一步可以是：为确认范围也维护一个 epoch / 指纹，范围没变就不要重建 `TrashScope`。粗估 **0.5–1.5 天**。这是 r8 的自然收尾，体量小；可留在 M5 收口或 M6 技术债，不必单独当产品功能。
3. **启动路径**：启动默认会扫盘（可用 `OPENPICASA_NO_STARTUP_SCAN=1` 关掉，这不是设置项）。之后 `tick_startup_verify`（增量校验，内部限速）与周期 L2 全校（6/24 h、等空闲）。扫描事件曾按目录刷，已有 `flush_reload` 节流。残留风险是大库冷启动时首屏与校验抢资源——**缺实测**，不建议在无基线时做大改。M6 更适合先规定「冷启动到首屏可交互」的测量方法。
4. **标签计数**：已在后台线程全量聚合（`TagCountsService`），UI 只读缓存；全库快路径是 `SELECT label, COUNT(*) FROM tags GROUP BY label`。**不是**写路径上的 ±n 增量，每次也新开一条 DB 连接并做迁移检查。对侧栏数字一般够用；只有在真实大库上测到可见停顿时，才值得做连接复用或增量（见第 6 问）。
5. **其它已相对克制、不要误当成下一刀**：栅格纹理每帧限量上传；胶片条只预取可见格；侧栏标签 / 相册脏时才查库；查看器标签按 `tags_for` 幂等，避免每帧拿 DB 锁（注释里记过启动首帧 hang 127 s 的教训）；监视器同步每 120 帧一次。这些不是当前主痛点。

下一步优化建议（在不回退 r8 的前提下）：**优先查看器预加载 / 取消 / 去黑帧 + EXIF 改读库**；可选给确认框范围比较做 O(1) epoch；冷启动与标签增量先测量再决定。不要为了「再扫一遍每帧」去动已经有界的预览缓存。

- 工作区 `Cargo.toml`：`heic = "0.1.6"`、`rawler = { version = "0.8", default-features = false }`，由 `picasa-imaging` **直接依赖**。

  - `heic-0.1.6` 的 `license = "AGPL-3.0-only OR LicenseRef-Imazen-Commercial"`，仓库 `https://github.com/imazen/heic`。README：双许可为 AGPL v3 或 Imazen 商业许可；并写明这只授权**版权**，HEVC 等**专利**不在该版权许可范围内，使用方需自行判断。
  - `rawler-0.8.0` 的 `license = "LGPL-2.1"`，仓库 `https://github.com/dnglab/dnglab`。
- 解码路径：`decode.rs` 里 `heic::DecoderConfig::new().decode(...)`；RAW 走 `rawler::get_decoder`，**优先嵌入预览**，没有嵌入图时**不**做 full develop，直接报「RAW 无嵌入缩略图，full develop 尚未启用」。没有独立 `raw-decoder` 子进程。Rust 默认把依赖**静态链进**成像库 / 最终二进制。
- SVG：只能 `sniff` 识别；注释把栅格化留给 `resvg`，但工作区清单仍把 `resvg / usvg` 列为未引入。筛选里有 SVG，不等于能预览。
- 工作区根 `license = "MIT OR Apache-2.0"` 与上述依赖并不自动一致。根 `Cargo.toml` 里仍有过时注释「M1 显式不引入 rawler / rawloader (LGPL-2.1, M2)」——**与现行依赖矛盾**，不能再当合规依据。

**可执行的工程选项（供法务 / 采购一起看；本文不给法律结论）：**

| 选项 | 含义 | 工程影响 | 不确定性 |
| --- | --- | --- | --- |
| 采购 Imazen 商业许可并保留 `heic` | 走 crate 声明的商业分支 | 代码改动最小 | 商务条款、费用、义务、与 HEVC 专利是不是两回事，均须法务确认。README 上的价目本轮不当成已谈妥的条件。 |
| 替换 HEIC/AVIF 解码器 | 例如平台 API（macOS ImageIO、Windows 解码器）或其它许可更清晰的库；`libheif` 会引入 C 与 HEVC 专利池，仓库自己都曾因此不用它 | 要换 `decode_heif_bytes`、重做实样、可能按平台拆分 | 专利与各平台质量差异 |
| 以 AGPL 方式开源发行整个付费二进制所含作品 | 可能与「买断闭源桌面软件」的产品目标冲突 | 发行与源码提供流程 | 是否满足 AGPL 对「分发」的要求，须法务判断 |
| 去掉或降级 HEIC | 不链 `heic`，HEIC 进失败队列 / 仅显示「不支持」 | 合规面变小，市场「广格式」变弱（iPhone 用户尤其明显） | 产品能否接受 |
| rawler：子进程隔离 | 架构文档曾经写过「主程序不链接、独立解码进程」；现行树**没做** | 满足 LGPL「用户可替换该组件」的常见工程做法之一；要定义进程协议、崩溃隔离、体积与启动成本 | 是否充分满足 LGPL，须法务 + 工程一起看 |
| rawler：动态链接 + 源码 / 目标文件提供 | 提供替换 .so/.dll 与重链说明 | 与目前纯静态 Rust 发布方式不同，安装包与签名都要改 | 静态 Rust 是否已满足「提供目标文件 + 重链权」，本轮**不下结论** |
| 去掉 rawler，只靠通用容器里的嵌入 JPEG | 许多 RAW 会失去预览（当前本来也已经「无嵌入就失败」） | 合规面变小，RAW「能看见」变弱 | 实样覆盖后才能判断可接受比例 |

建议：

- **付费二进制分发前**，把 `heic` / `rawler` 作为销售门闩，而不是先做支付页。这与已批「OpenPicasa 待依赖许可审查后再公开销售」一致。
- 工程上可并行准备的（仍须专项批准，不是现在开工）：完整 `cargo tree` / `cargo deny` 审计、按格式的实样矩阵（JPEG/HEIC/WebP/TIFF/RAW/SVG）、以及一份「保留 / 采购 / 替换 / 降级」对照表。SVG 栅格化是单独的功能缺口（还要单独看 `resvg` 的 MPL-2.0 义务），不要和 HEIC 混成一个许可决定。
- 不要在市场材料里写「已支持 RAW 全画质显影」：现行路径在无嵌入预览时是失败，不是 full develop。

本轮未请法务审阅，以上只是依赖事实与工程选项。

## 9. 对产品已列讨论项的技术含义（不发明产品决定）

- **翻页 / 冷启动基线**：值得作为 M6 技术包的测量与治理主项。现行没有 M5 通过记录。要先约定机器、图库和指标，再谈「阻塞治理」。只改 DB 查询无法代替整机冷启动与大图连翻。
- **真 100% 口径**：必须先做产品裁决（第 2 问）。不裁决就开工，很容易做成「解 100 MP 整图上传」或「按钮叫 100%、实际仍是 2560」。
- **格式实样与依赖许可**：技术上已能解码多种格式，但实样与合规都未收口，这会挡住公开销售。应与许可专项分开跟踪，但时间上要排在公开销售之前。
- **并排比较是否升级为可同步的缩放 / 平移**：现行右窗格永远适屏，与左图缩放无关。做成「可解锁的同步」是加法（两窗格共享 zoom/pan，或做链接开关），不破坏「无第二张不画假图」。工作量粗估 **2–4 天**；不要和真 100% 分块绑死，但若 100% 改成图块，同步比较要一起设计视口。
- **P1 独立帮助页**：M5 已裁定本阶段不做；若进 M6，主要是文案与信息架构，技术风险低（**约 1–3 天**），但会碰到「入口放哪」——不要塞进设置页正文来绕开 §11。
- **P1 接通幻灯片**：顶栏按钮已在，现状是「下一版开放」toast。接通是正式承诺：全屏播放、间隔、键盘退出、与预加载管线的关系。建议等翻页预加载有雏形再做，否则幻灯片只会把第 3 问的黑帧放大。粗估在预加载之后 **3–7 天**。
- **P1 渐进预览（P-M43-07）**：先完成第 5 问的裁决与 v10 计划；技术可行，但不是小修，且与「失败不产生半库」强相关。
