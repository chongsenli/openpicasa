## 2. 与规格的偏差（**逐条理由**）

### 2.1 schema 与命名

| 规格写法 | 本仓库 | 理由 |
| --- | --- | --- |
| `photos.filename` | `photos.name` | v1 就叫 `name`，改名要重建表 |
| `idx_photos_folder_name(folder_id, filename)` | 复用已有 `idx_photos_folder(folder_id, name_key)` | 同一件事，不重复建（写放大） |
| `folders.rel_path` 范围索引 | `idx_folders_root_path(root_id, path_key)` | 本仓库存绝对路径；`path_key` 前缀范围同样走索引，加 `rel_path` 要整列回填 |
| `settings` 表「已有」 | **实际没有**，v6 新建 | M2 的设置全在 Preferences JSON 里；分工见 §2.4 |
| `folders.dir_mtime`（秒） | **纳秒** | 见 §2.2 —— 这是本文最重要的一条 |

### 2.2 ⚠️ `dir_mtime` 存纳秒而不是秒

`07` §8.1 的 DDL 注释写「目录 `st_mtime`（秒）」。实现存的是**纳秒**。

**这是有意的，而且是被用例逼出来的**：L1 的判据是「目录 mtime 有没有变」。
秒级精度 + 2 秒容差（`MTIME_TOLERANCE_S`，为 exFAT 的量化相位差而设）会
**吞掉「同一秒内新增的文件」**——而那正是「拷进 1000 张照片」的场景：
目录 mtime 一直在同一秒里跳，L1 每次都说「没变」，用户的照片永远进不来。

两者误差代价不对称：

| | 判成「有变化」 | 判成「没变化」 |
| --- | --- | --- |
| L1 目录 | 多扫一个目录（可接受） | **用户的改动被静默丢弃**（不可接受） |

所以 L1 用精确纳秒（宁可外置盘重挂后多跑一次全校，它会自我修复），
**L2 的文件级比对仍然用 2 秒容差**（那里容差是必要的，且 L2 本来就是兜底）。

> 用例：`m3_verify_l1l2.rs::tc_m3_verify_l1_detects_an_added_file`

### 2.3 「关闭子目录」的语义

`07` §4.3 COUNT-03 写「关闭子目录 → 祖先 `total` 立即减少」。
本仓库**子目录没有独立开关**——用户的「关闭」只发生在**根**这一级（`roots.state`）。
屏蔽某个子目录走**排除项**（`exclusions`），而排除项根本不进 `folders` 表。

所以 COUNT-03 的可观测行为用「删掉该目录的索引行」验证：
祖先 `total` 跟着变、`direct` 不变。语义等价，实现路径不同。

> 用例：`m3_count.rs::tc_m3_count_003_closing_a_subfolder_reduces_the_ancestor_total`

### 2.4 `Preferences` 与 `settings` 的分工

`07-A` §6 假定 `settings` 表已存在。本仓库的划分：

| 存哪 | 存什么 | 为什么 |
| --- | --- | --- |
| `Preferences`（JSON） | 窗口几何、折叠状态、上次视图、栅格滚动位置 | **这台机器的界面状态**，换个窗口大小不该改变语义 |
| `settings`（DB） | `grid_cell_px`、`recurse_subfolders` | **跟库走的行为开关**，必须能被迁移脚本预置、能被 SQL 查询 |

### 2.5 键集分页只覆盖「按拍摄时间」

`07` §5.2 SCALE-03 要求所有排序都用键集。实际只有 `SortKey::TakenAt` 走键集，
其余（大小 / 修改时间 / 文件名）仍用 `OFFSET`。

判据是「有没有一条以排序键打头的复合索引」：

| 排序键 | 可用索引 | 键集 |
| --- | --- | --- |
| `TakenAt` | v6 的 `idx_photos_taken_id (taken_at, id)` | ✅ |
| `Size` | 只有 `idx_photos_size_mtime (folder_id, …)`，前导列是 folder_id | ❌ |
| `ModifiedAt` | 只有 `mtime_ns DESC` 单列 | ❌ |
| `Name` / `Dimensions` | 键是 TEXT / 表达式 | ❌ |

硬走键集但索引不匹配的后果是「全表扫描 + 临时 B 树排序」，**比 OFFSET 更慢，
而且结果完全正确**——这种退化只有执行计划能发现。
补齐其余索引是 M4 的事（`08` §3.5 的 `idx_photos_size_id` 等）。

> 用例：`m3_scale.rs::tc_m3_scale_003_keyset_plan_uses_an_index`（断言无 `SCAN` 与无临时 B 树）

### 2.6 `head_hash` 用双通道 FNV-1a 而不是 blake3

本仓库没有 `blake3` 依赖。为一个**消歧辅助**拉一棵新依赖树不划算。

判据是「前 64 KB 逐字节相同」，而双通道 FNV-1a（两个不同初值与混合顺序）拼 16 字节
对随机差异的碰撞率约 2^-64。真正的风险是**恶意构造碰撞**——而这里的输入是
用户自己的照片，不是攻击面。

`[u8; 32]` 的类型保持不变，将来接 `blake3` 只换 `movematch::head_hash` 一个函数。

> P-22 建议先只用 `(size, mtime)`，统计歧义率 > 1% 再开 `head_hash`——
> 所以这里的实现是**惰性**的：单候选一次都不读盘。

### 2.7 同目录改名：完全不可区分的候选按序配对（与跨目录不同）

- **跨目录移动**：多候选 + 无哈希 → **拒绝配对**（猜错会让「A 的星标跑到 B 身上」，
  比星标消失更让人不信任软件）。
- **同目录改名**：多候选 + 无哈希 → **按序一对一配**。

理由：同目录的 `removed` 与 `added` 来自**同一次扫描**，数量与指纹一一对应；
而跨目录的 `added` 可能来自完全不同的目录，「凑巧大小 mtime 一样」的概率高得多。

### 2.8 L2 周期调度：按「批」而不是按「全量」轮转

`07` §3.2 VERIFY-03 已实现（`FullVerifyScheduler` + `folders_due_for_verify`），
但有一处**语义选择**与规格的字面读法不同：

规格写「每轮最多 `VERIFY_FULL_BATCH`（200）个」，隐含「一轮 = 200 个目录」。
本实现把「轮」定义为「一次启动调度」，而**每批 200 个**是这一轮里反复取的
——因为 `folders_due_for_verify` 是「最久没校验的 200 个」，
跑完之后它们变成「刚校验过」，下一次调用自然取到**下一批 200 个**。

所以实际行为是：每 6/24 小时「开始」一轮，这一轮里按 200 个一批把积压全部走完。
这比「每 6 小时只校 200 个」更符合用户预期——后者在 4330 目录的库上要 21 轮、
5 天才轮完一遍。

**空闲判据**是 `!索引任务在跑 && 启动校验已结束 && !正在拖滑块`。
前两条是硬要求（抢 IO），第三条是体验（拖滑块时每帧重排，再叠 stat 循环会发涩）。

⚠️ `ORDER BY` **不能**写 `last_verified_at IS NOT NULL, last_verified_at`——
那个表达式会让 SQLite 放弃索引走 `USE TEMP B-TREE FOR ORDER BY`。
SQLite 的 ASC 排序本来就把 NULL 排最前，正是我们要的。

> 用例：`m3_verify_l1l2.rs` 的 `tc_m3_verify_003_*` 五条 + `due_for_verify_query_uses_the_v6_index`

### 2.9 微缩图集只有「判定」，没有「渲染」

`07-A` §A-2.2 / P-57 ② 要求 ≤ 48 px 走微缩图集。本版实现了：

- `zoom::uses_atlas(px)` 的**判定**（22～48 走图集）
- `texbudget` 的字节预算（图集要遵守同一份预算）

**没实现**的是图集渲染本身（打包进 4096² 纹理、按 UV 绘制、LRU 整张淘汰）——
那部分在 `picasa-ui` 的渲染层，需要 `TextureHandle` 与自定义绘制，
是独立的一轮工作。分工的理由与 `TextureBudget` 相同：策略能脱离 GPU 单测。

在它落地之前，22～48 px 仍然走「T0 纹理缩着画」——能用，只是不如图集省内存。

### 2.10 `BoundedQueue` 用 `VecDeque` + Mutex 而不是 `sync_channel`

`watch.event_chan = 8192` 要的是**容量**，而 `sync_channel(n)` 满了会让**发送方阻塞**。
发送方是 notify 的 callback（跑在它的内部线程），阻塞在那里等于把整个 FSEvents
事件循环卡住——那时连「丢弃」都做不到。

所以实现是「满了就丢最旧的 + 计数」，丢弃数变成 `WatchState::Overflow`。

### 2.11 平台探测用 `df` 而不是 `statfs`

本仓库刻意保持依赖树小（没有 `libc`）。`df -P` 的输出解析在 macOS / Linux
上都够用，而且**只在装监视时跑一次**（不是热路径）。

失败时保守返回 `false`（当作本地盘）：宁可试着装监视（装不上会自己降级成
`BackendError`），也不要因为探测失败就把本地盘当网络卷、白白退化成轮询。

### 2.12 畸形样本用「生成」而不是「提交二进制」

`07-A` §4.3 要求 `fixtures/formats/malformed/` 每格式 ≥ 20 个，**并进仓库**。

本实现的选择是：**用代码描述每一类畸形**（`picasa-imaging::fixtures`），
测试时生成到临时目录再真跑解码。每个格式 4～9 个样本，**不是 20 个**。

理由：

- 提交 200 个二进制会让仓库变重，且 review 时看不出「这个样本畸形在哪」
- 想加一类新畸形（比如「IFD 偏移指向自己」）要再造一个文件；用代码只改一个函数
- **20 个同质样本不会比 5 个异质样本多发现一个 bug**

规格那句话的**目的**是「解码器对畸形输入不崩」，不是「必须有 200 个文件」。
本实现覆盖 7 类失败模式（截断 / 头部篡改 / 尺寸溢出 / 循环引用 / 空文件 /
巨型声称 / 非图像字节），并把每条的 intent 写进结构体——失败时能直接看出是哪类没被拦住。

**实测**：43 个样本全部在 5.7 ms 内处理完，零 panic、零挂起，
每个都返回 typed error 进可见失败队列。

> 用例：`malformed_does_not_crash.rs`（4 条）、`fixtures.rs`（6 条单测）、
> `m3_guard_decode.rs`（2 条接线）

## 2bis. M3 自身修掉的三个真 bug

写代码时撞出来的，**每一个都不报错、只表现为「结果不对」**——这类最容易漏到用户手里。

| bug | 表现 | 怎么发现的 |
| --- | --- | --- |
| 键集平局键与 `ORDER BY` 不一致 | 400 张同一秒的库里翻页只取回 **69** 张 | 造了「名字顺序与 id 顺序无关」的数据才暴露；名字按序生成时两种顺序同构，用例白写 |
| `DataSource::range` 窗口起点与返回行错位 `pad` 行 | 滚出第一个窗口后翻页漏照片 | `tc_m3_scale_003b`（500 张同秒逐页翻） |
| `settle()` 首次必定返回 `Some` | 每个新视图白请求一轮同档纹理 | 拖动用例断言「拖动期间零档位请求」时值不为 0 |
| `apply_scan` 不写 `dir_mtime` | **L1 完全退化**：每次启动仍走完整 L2（20 分钟），且不报错 | 在真实库副本上扫一次后 `SELECT COUNT(*) ... WHERE dir_mtime IS NOT NULL` 得到 0 |

第一条的修法值得记：游标平局必须用 `name_key`（`ORDER BY` 里那一列），
不能用 `id`。**并且**拼字符串字面量要用 `sql_text_literal` 而不是 `escape_like`
（后者转义 `%` `_` `\` 是给 `LIKE` 用的）。

> 守卫：`m3_scale.rs::keyset_tiebreak_follows_name_key_not_id`、
> `m3_verify_l1l2.rs::apply_scan_writes_dir_mtime_in_the_same_step`

第四条特别值得记：**它的症状是「什么都没发生」**。单测抓不到它，因为 v6 的
补数**故意不填** `dir_mtime`（`07` §8.2：空 = 还没量过 = 走 L2）——
只有「真的扫一次」之后才该有值，而那一步之前没有用例覆盖。
发现方式是在真实库副本上跑完迁移再查一次 SQL。

## 6. 给下一个人的三条提醒

1. **`dir_mtime` 是纳秒**（§2.2）。改回秒会让「同一秒内拷进 1000 张」静默失效，
   而症状是「用户说他在外面加了照片，软件不知道」——极难归因。
2. **拖动中不换纹理**（`zoom::ZoomState::settle` 在 `dragging` 时返回 `None`）。
   有人可能觉得「拖动时实时换档更跟手」而删掉这个判断——那会让拖动期间每帧
   重启一轮解码，弱机上直接掉到 10 fps 以下。
3. **熔断的粒度是格式，不是文件**（`format::DecodeGuard`）。改成逐文件熔断等于
   没有熔断：坏目录里每个文件都是「新的」，都值得试一次，流水线会一直崩下去。
