### 0.4 【§2】PERF-08 的问题：限制纹理内存的是**我们的 LRU，不是 egui 默认行为**

| 问 | 答 |
| --- | --- |
| 当前什么在限制显存/纹理占用？ | `crates/picasa-ui/src/textures.rs::TextureCache`：自管 `HashMap<i64, TextureHandle>` + `VecDeque<i64>` LRU，上限 **`Metrics::TEX_CACHE_CAP = 120` 张**（512×384×4 ≈ 786 KB/张 → **≈ 92 MB**）。`upload()` 后立即 `evict_if_needed()`，淘汰时 `drop(tex)` 主动释放 GPU 纹理、不等 egui 延迟回收。 |
| M2.1 的 LRU 还在吗？ | **在**，未被 M2.2 改动。 |
| egui 默认行为是限制者吗？ | **不是**。egui 只持有我们 `ctx.load_texture()` 传进去的句柄（`TextureOptions::LINEAR`），淘汰决策完全在我们这边。 |
| 与 PERF-08 的差距 | 规格要按**「与视口距离（屏数）」加权**（距离 0 永不淘汰、≥3 优先淘汰），当前是**纯 LRU**（只按最近使用时间）→ 会出现"刚滚过、还在视口边缘的图被淘汰"的抖动；且上限按**张数**而非 `texture_cache_mb`（MB）。 |
| 内存门禁是否因此免除？ | **不免除**。5 万张 ≤ 1.0 GB / 静置回落仍需实测；P-19（384 MB 是否过大）随之保持后置，我同意。 |

## 6.5 死机修复记录（2026-11-01 · 点「索引」按钮界面冻结 90 秒）

### 现象

在 25.9 万张 / 1.40 GB 的真实库上，点状态栏索引入口 → 界面冻结无法操作。

### 根因（实测，不是推测）

`refresh_mgmt()` 在 **UI 线程同步**跑 `build_snapshot()`，而后者里含两条 BLOB 全表扫描：
`root_stats()` 对每个根做 `SUM(LENGTH(t.data))`，`cache_stats()` 做一次全 thumbs 求和。
管理页打开期间还按 4 Hz 反复触发。

关键实测数据（`library.sqlite`，1.40 GB，thumbs 35 090 条 / 1.26 GB）：

| 查询 | 耗时 |
| --- | --- |
| `thumbs JOIN photos JOIN folders … GROUP BY root_id` | **112 s** |
| `WHERE photo_id IN (SELECT …)` | 23 s／根 |
| **`WHERE EXISTS (SELECT …)`** | **0.28 s／根（热缓存 0.06 s）** |
| 裸 `SUM(LENGTH(data)) FROM thumbs`（无 JOIN） | 0.019 s |
| 旧 `root_stats` 去掉 BLOB 求和后 | 1.025 s |
| 按 `folders.direct_count` 分组求和 | **0.002 s** |

**为什么 `EXISTS` 快 400 倍**：SQLite 对 `LENGTH(blob)` 有「列宽记在记录头、不读溢出页」的优化。
写成 `JOIN` 后优化器物化整行，1.26 GB 溢出页被逐字节读出；`EXISTS` 是半连接，不物化 `thumbs` 行，优化得以保留。

### 改了什么

| 层 | 改动 |
| --- | --- |
| `picasa-db` | `root_stats()` 改用「对 `folders` 分组求和 + 按根分组数失败项」，**不再带** `thumb_bytes`；新增 `root_thumb_bytes()`（`EXISTS` 写法，文档里写清为什么不能改回 `JOIN`）、`thumb_cache_stats()`、`db_bytes()`、`photo_count_total()` |
| `picasa-core` | `build_snapshot()` **不再碰 thumbs 表**；新增 `ThumbStorage` / `collect_storage()` / `apply_storage()`；`StorageView` 增 `thumb_stats_known` |
| `picasa-ui` | 快照刷新 4 Hz → **1 Hz**（仍满足 §6.1 的「≤ 4 次/秒」）；缩略图统计改由**后台线程**算，`try_lock` **逐根短锁**（整段一次长锁实测 2.2 s，会把 UI 的库访问全堵住）；缓存 TTL 30 s；未算完界面显示「计算中…」而不是 0 |
| 测试 | 新增 `crates/picasa-db/tests/root_thumb_bytes.rs` **4 条**：`EXISTS` 与朴素 `JOIN` 逐根对拍、未知根给 0、`thumb_cache_stats` 对拍、`root_stats` 计数与逐行 `COUNT` 对拍 |

修复后实测（`cargo run --example mgmt_timing`，真实库）：

```
root_stats                  0.242s
build_snapshot #0          0.589s     ← 冷缓存首帧
build_snapshot #1          0.097s     ← 热缓存，1 Hz 刷新 → 约 10% 主线程
build_snapshot #2          0.089s
collect_storage(后台)        2.222s     ← 已不在 UI 线程
```

### 仍存在的风险（不隐瞒）

- 冷缓存**首次**点开管理页仍有约 0.6 s 的同步查询（`mgmt_counts` + `root_stats`）。可接受，未再做异步化。
- 后台统计期间 `Db` 被逐根短锁占用，单次最长约 0.7 s；极端情况下仍可能有可感知的顿挫。
  彻底解法是给后台线程一条**独立只读连接**，本次未做（WAL 下 read-only 连接需 `-shm` 可写，有失败模式，需单独验证）。
- 计时程序 `crates/picasa-core/examples/mgmt_timing.rs` 保留，正是评审 §6 第 3 步要的 `perf_bench` 的雏形。
