### 0.2 四条设计原则

| 原则 | 含义 | 可判定性 |
| --- | --- | --- |
| **一次迁移，覆盖全部改动** | 宽高相关字段、`roots`、`folders` 扩展、排除表、任务与失败记录在**同一次**升级完成，用户只经历一次"正在升级资料库" | `SCHEMA_VERSION` 从 1 直接到 2，中间不出 1.5 |
| **只增不改** | 只 `ADD COLUMN` / `CREATE TABLE` / `CREATE INDEX`，**不修改任何已有列的语义，不重写已有行**（唯一例外见 §1.3.1 的 `orientation` 空值归一） | 迁移脚本里不出现 `DROP` / 列类型变更 |

| **照片目录零写入** | 迁移只操作应用自身数据库与缓存目录 | `TC-IDX-020` 的清单比对口径继续有效 |

## 1. 第一部分：数据层技术设计

### 1.1 与现有 schema 的关系（先读这段）

M2 A 线落地时**没有动 schema**：`SCHEMA_VERSION = 1`，`MIGRATIONS` 只有 `m1_minimal` 一条（`crates/picasa-db/src/schema.rs`）。因此：

- **M2.1 的迁移是 `version = 2`**，追加在 `MIGRATIONS` 数组末尾，不改 v1 脚本。
- 判定"当前是 M2"要用 `Db::schema_version() == 1`（读 `schema_migrations` 的 `MAX(version)`），**不是 `PRAGMA user_version`**——本项目没有用那个 PRAGMA。
- 迁移框架自带"已应用的跳过"（`if m.version <= current { continue }`），所以**幂等由框架保证**，SQL 里不需要写 `IF NOT EXISTS` 兜底；需要幂等的是"由照片推导文件夹"那一步（见 §1.4.2）。

### 1.2 对账表：初稿 ↔ 代码实际 ↔ 本版裁决

| # | 初稿写法 | 代码实际 | **本版裁决** |
| --- | --- | --- | --- |
| 1 | 检查 `PRAGMA user_version` 确认 M2 版本 | 迁移框架是 `schema_migrations` + 顺序数组，且**当前仍是 v1**（M2 未升版） | 用 `schema_version() == 1` 判定；本版迁移为 **v2** |
| 2 | `photos.folder_id` **新增** | 已存在，`REFERENCES folders(id) ON DELETE CASCADE` | **不加**，直接复用 |
| 3 | **新增**文件夹表 | `folders` 已存在（每目录一行、`path` UNIQUE、`volume_id`、`thumb_tier`），只缺层级字段 | **扩展** `folders`（加 `parent_id`/`root_id`/`name`/`direct_count`/`has_children`/`index_status`），不新建表。省 1 人天 |
| 4 | 根文件夹表**扩展**加 `state`/`closed_at` | **没有根文件夹表**。关注目录在 `Preferences.roots: Vec<String>`（`picasa-core/src/prefs.rs`） | **新建 `roots` 表**，并把 `prefs.roots` 一次性迁入；迁入后 prefs 的 `roots` 字段标废弃（保留 3 个版本用于回读，不再写入）。**不迁就是双真相源，按 P0 处理** |
| 5 | 新增 `pixel_width`/`pixel_height`/`orientation` | `width` / `height` / `orientation` **都已存在** | **复用**，不新增 pixel_*。只补 `dims_status`；`display_width`/`display_height` 用 **VIRTUAL 生成列**（§1.3.1） |
| 6 | 索引 `photos(folder_id, sort_key)` | **没有 `sort_key` 列**。排序是查询期参数 `SortSpec`；已有 `idx_photos_folder(folder_id, name_key)` | 按真实排序建索引（§1.3.6），**name 排序已有索引，不重复建** |

### 1.3 表结构变更（迁移 v2）

#### 1.3.1 `photos`：只加 1 列

| 新增 | 类型 | 说明 |
| --- | --- | --- |
| `dims_status` | INTEGER NOT NULL DEFAULT 0 | 0 待回填 / 1 已完成 / 2 读取失败 |

`display_width` / `display_height` **不做普通列**，用生成列（读时计算，不占空间、不可能与 `orientation` 不一致）：

```sql
ALTER TABLE photos ADD COLUMN display_width INTEGER
  GENERATED ALWAYS AS (CASE WHEN orientation BETWEEN 5 AND 8 THEN height ELSE width END) VIRTUAL;
ALTER TABLE photos ADD COLUMN display_height INTEGER
  GENERATED ALWAYS AS (CASE WHEN orientation BETWEEN 5 AND 8 THEN width  ELSE height END) VIRTUAL;
```

- `orientation` 为 NULL 时 `NULL BETWEEN 5 AND 8` 求值为 NULL → 走 `ELSE` 分支，取 `width`/`height`，不会变成 NULL 方向。
- ⚠️ **SQLite 限制：`ALTER TABLE ADD COLUMN` 不允许加 STORED 生成列，只能用 VIRTUAL**。VIRTUAL 列不进索引，M3 瀑布流只读不筛，够用；若 M5 需要按显示宽高筛选，届时再考虑物化。
- 折算规则：`orientation ∈ 5..8` → 宽高互换；其余（含缺失）→ 原样。

`orientation` 的空值归一（**唯一一处"改写已有行"**）：`UPDATE photos SET orientation = 1 WHERE orientation IS NULL;`。理由：初稿要求"缺失记为 1"，而生成列的 `ELSE` 分支虽能兜住 NULL，但 M4 的旋转叠加要读 `orientation` 做算术，NULL 会一路传染。这一步只碰 NULL 行，且幂等。

#### 1.3.2 `roots`（新建）—— 承接 `Preferences.roots`

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `path` | 绝对路径（NFC），UNIQUE |
| `path_key` | 比较键（NFC + 大小写规则） |
| `state` | 0 `active` / 1 `closed`。关闭只改状态，**不删数据** |
| `added_at` / `closed_at` | 加入 / 关闭时间 |
| `case_insensitive` | **该卷是否不区分大小写（探测一次后固化）** |

重新添加同一路径时，匹配到 `state = closed` 的记录则置回 `active`、复用 `root_id`，排除记录原样沿用——实现"再次添加秒开"。

`case_insensitive` 固化在库里是本节的关键裁决：初稿写"根据卷是否区分大小写决定"，但**判定手段全是 macOS 专有思路**（`diskutil`）。这个项目主交付 macOS 但 Linux 已提前打通（README §快速开始），开发与测试都在 Linux 上跑。**统一的可移植探测**：

1. 对根目录下任一已存在条目，尝试 `lstat`「全大写」与「全小写」两个变体；
2. 两个变体都能命中同一 inode → 不区分大小写 → 1；只有一个命中 → 区分大小写 → 0；
3. 目录为空或探测失败 → 取默认 **1**（宁可多归一，不要漏判：漏判会导致"关闭 `Photos` 对 `photos` 不生效"，这比多归一更难排查）；
4. 结果**只探测一次并落库**，扫描时直接读列，不重复探测。

#### 1.3.3 `folders`（扩展）

| 新增字段 | 说明 |
| --- | --- |
| `root_id` | 所属根目录 → `roots(id)` |
| `parent_id` | 父文件夹，根目录为 NULL |
| `name` | 显示名（末段） |
| `direct_count` | 本目录**直接包含的有效照片数** |
| `has_children` | 是否有子目录（树节点画展开箭头不必再查） |
| `index_status` | 0 空闲 / 1 索引中 / 2 失败 / 3 部分失败 |

文件夹树完全从这张表读，展开节点只需 `WHERE parent_id = ?`，是 O(直接子节点数) 而不是全表扫。

**✅ 已裁决（P-07）：`direct_count` 是物理事实，不受关闭状态影响。** 关闭一个目录只改变"树里是否显示"，不改变"它有几张照片"。M3 的递归计数因此拆两列：`total`（物理，含已关闭子树）与 `visible`（扣除已关闭子树，用于"当前视图显示多少张"）。两套口径各有明确定义，就不会打架。

#### 1.3.4 `exclusions`（新建）

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `root_id` | 所属根目录 |
| `relative_path` | 归一化相对路径（NFC，原样保留供展示） |
| `match_key` | 比较键 = NFC + （`roots.case_insensitive = 1` 时小写） |
| `created_at` | 创建时间 |
| `stale` | 路径已不存在 → 1，供诊断页清理 |

`UNIQUE(root_id, match_key)`：同一路径不允许重复排除。

#### 1.3.5 索引任务与失败记录（新建）

**`index_tasks`**：`task_id`、`root_id`、`scope_path`、`kind`（0 首次索引 / 1 刷新 / 2 重新索引 / 3 恢复 / 4 回填）、`status`（与 04 §3.1 的七态一一对应，用同一套整数编码）、`started_at`、`finished_at`、`error_code`。

**`index_task_failures`**：`task_id`、`relative_path`、`error_code`、`attempts`、`updated_at`，主键 `(task_id, relative_path)`。

> **⚠️ 真相源边界（必须写进实现注释）**：**实时进度**的真相源仍是内存里的 `IndexBoard`（04 §3.2 的四处一致靠它）；**历史失败记录**的真相源是 `index_task_failures`。两者只通过 `task_id` 关联，**DB 不参与实时进度计算**。跨过去就会退化成"两个计数器"，那是 04 判定的 P0。

#### 1.3.6 索引清单

| 索引 | 用途 | 说明 |
| --- | --- | --- |
| `photos(folder_id, taken_at DESC)` | 选中节点后按拍摄时间分页 | **新增** |
| `idx_photos_folder(folder_id, name_key)` | 按文件名分页 | **已存在，复用** |
| `photos(dims_status) WHERE dims_status = 0` | 部分索引，后台回填快速取待处理 | **新增** |
| `folders(parent_id)` | 树节点展开 | **新增** |
| `exclusions(root_id, match_key)` | 排除判定 | **新增** |
| `roots(path_key)` | 添加/复用根目录时匹配 | **新增** |

> 初稿的 `sort_key` 列不存在，按真实排序建索引即可。`mtime` 排序已有 `idx_photos_mtime`，M2.1 不另加。

### 1.4 迁移流程（v1 → v2）

1. **判定**：`schema_version()` 必须为 1。为 0（新库）则直接建 v1 再建 v2；为 ≥2 则跳过。
2. **备份**：`VACUUM INTO '<数据目录>/Backups/openpicasa-v1-<utc>.db'`。
3. **单事务**：`BEGIN IMMEDIATE` → 建 `roots` → `ALTER folders` → `ALTER photos` → 建 `exclusions` / `index_tasks` / `index_task_failures` → 建索引 → `COMMIT`。
4. **迁 roots**：读 `Preferences.roots`，逐条 `INSERT INTO roots`（`added_at` 取 preferences 文件 mtime，精确值不可得，不编造）。
5. **推导 folders**：遍历 `photos` 的路径，在 Rust 侧做 NFC 归一 + 拆段 + 补父链，写 `folders` 并回填 `folder_id` / `direct_count` / `has_children` / `parent_id`。
6. **置待回填**：`UPDATE photos SET dims_status = 0`，交给按需回填与后台批量回填。
7. **收尾**：失败则回滚事务 + 用备份恢复 + 写诊断日志，应用以 M2 数据继续运行；成功则显示"正在升级资料库"消失。

#### 1.4.1 为什么备份必须是 `VACUUM INTO`

库开着 **WAL**（`PRAGMA journal_mode = WAL`）。未 checkpoint 的事务在 `-wal` 文件里，**只 `cp` 那个 `.db` 会拿到一个缺事务的库**。而"先 checkpoint 再拷"又要求没有活跃读者——索引线程还在跑时必然失败。

`VACUUM INTO` 一次搞定：它是读事务语义、产物是自洽的完整库、还顺带整理碎片。代价是临时多占一份库大小的空间，迁移前要先检查剩余空间。

#### 1.4.2 NFC 归一必须在 Rust 侧做（初稿"用 SQL 推导"不成立）

初稿第 4 步写"用 SQL 从已有照片路径提取目录，这一步只读数据库，不访问文件系统"。**拆路径可以做，NFC 归一做不到**——SQLite 没有 Unicode 归一化函数，`substr`/`instr` 拿到的仍是原样字节。而 04 与本文都要求统一 NFC 存储（否则 HFS+ 的 NFD 目录名永远匹配不上 APFS 的 NFC 记录）。

因此第 5 步**必然是 Rust 侧的一次读 → 归一 → 回写遍历**。5 万行的 5 秒预算，主要消耗就在这一步，不在 DDL。

> **⚠️ v1.1 更正**：v1.0 在这里写"`unicode-normalization` 已在依赖里"——**这是错的**。M1 只有
> `picasa-core::paths::nfc` 这个手写近似版（只预组合十来个拉丁字符对），它够用于"避免同一串
> 字符的两种编码产生两条索引"，但**不够用于一次性改写全库**。v1.1 已把 `unicode-normalization`
> 正式加进 workspace 依赖，`picasa-db` 的层级推导用它做归一（叶子 crate 不能反向依赖 core，
> 所以实现落在 db 侧的 `pathutil::nfc`）。

**幂等手段**：不 `DELETE` 全表（`folders` 被 `photos` 外键引用），而是
`UPDATE folders SET parent_id = COALESCE(parent_id, ?), ... WHERE id = ?`——已推导过的行不动，因此"回退到 M2、再升回来"时只会补齐新增部分。

### 1.5 排除判定

- 扫描时把该根目录的排除项按 `match_key` 加载为**内存 HashSet**，**进入目录时判定**，命中则跳过整棵子树，不逐文件判断。
- 栅格查询只按 `folder_id` 过滤，**不拼排除条件**：被关闭的节点在树里置灰，选中时显示"已关闭，可恢复"空状态。因此列表查询性能不受排除规则影响。

### 1.6 降级兼容（初稿结论是反的，已修正）

初稿写"因为只增不改，回退到 M2 旧版本仍可读取照片数据"。**这条与代码相反**：`Db::migrate()` 里有

```rust
if current > SCHEMA_VERSION { return Err(DbError::SchemaTooNew { .. }); }
```

库升到 v2 后，M2 的二进制（`SCHEMA_VERSION = 1`）会**直接拒绝打开数据库并退出**，不是"忽略新表继续读"。

**修正后的承诺（三级）**：

| 场景 | 行为 |
| --- | --- |
| 升级失败 | 回滚事务 + 恢复备份，M2 数据完好，应用正常启动 |
| 用户主动降级到 M2 | **不支持直接跑**。诊断页与升级完成提示必须写明"降级需用 `Backups/openpicasa-v1-*.db` 覆盖数据库" |
| 降级后再升回 M2.1 | 支持。迁移按 §1.4.2 的幂等补数，只补齐新增部分，不重算已有 |

> 不建议为了"支持降级"而放宽 `SchemaTooNew`。旧版本不认识生成列与新表，写入会留下半新半旧的数据，比拒绝启动危险得多。

### 1.9 落地记录（v1.3，C 工作包）

代码位置：`crates/picasa-db/src/{lib,schema,types,dims}.rs`（生成列 + 索引 + 列清单收口）、

`crates/picasa-ui/examples/c_bench.rs`（性能基线工具）、
`crates/picasa-db/tests/photo_columns.rs`（执行计划回归）。

**这一包的核心不是「加一个索引」，而是「排序用到的表达式必须落进一列，索引才用得上」。** 落地时
发现了一条规划阶段没写进去的事实，它直接决定了迁移要再加一版：

> 脏排序 `ORDER BY COALESCE(taken_at, mtime_ns / 1_000_000_000)` 是**表达式**，
> SQLite **不会**为 `ORDER BY` 里的表达式用上 `idx_photos_folder_taken(folder_id, taken_at DESC)`，
> 于是 5 万行的首页查询变成 **全表扫 + 全排序（199 ms）**。唯一的解法是把这个表达式固化为
> `photos` 表上的一个 **VIRTUAL 生成列 `eff_taken_at`**，再建
> `idx_photos_eff_taken(eff_taken_at DESC, name_key ASC)`——实测降到 **1.77 ms**。

| # | 本文原写法 | 实际落地 | 为什么改 |
| --- | --- | --- | --- |
| 1 | §1.3.6 只有 `idx_photos_folder_taken(folder_id, taken_at DESC)` | 新增 `eff_taken_at` **VIRTUAL 生成列** + `idx_photos_eff_taken`；schema 升到 **v3** | `taken_at` 可能为空（盘不在那天的照片），排序要按「有就用、没有就退到 mtime」，这个 COALESCE 是表达式，必须固化成列才能让索引生效。STORED 不可行（生成列在 SQLite 里 STORED 需要重建表，且本列不长算），VIRTUAL 够用——索引会即时算 |
| 2 | （未写）迁移失败降级到 v1/v2 时 SQL 仍要能跑 | `Db::eff_col()` 单一来源：v3 用 `p.eff_taken_at`，降级退回 `COALESCE(...)`；`SortSpec::order_by(eff)` 接受该表达式 | 否则 `open_with_report` 失败回滚到旧 schema 后，所有 SQL 硬引用 `p.eff_taken_at` → `no such column` 直接崩，等于「迁移失败 = 应用起不来」，与 §1.4「不拒绝启动」承诺相反 |
| 3 | （未写）8 处 SELECT 各写一份 `p.id, p.folder_id, ...` | 收口到 `Db::photo_cols()`，**全项目只此一份**；`map_photo` 下标与它成对 | 加 `eff_taken_at` 时漏改两处（B 工作包遗留同样的坑），运行期才炸 `InvalidColumnIndex`。收口后 `tests/photo_columns.rs` 把每条返回 `PhotoRow` 的查询真跑一遍，列数对不上立刻挂 |
| 4 | §2.1「大文件夹快速打开」只说「分页」 | `reload_photos` 改成两段式：先 `COUNT` 拿总数（O(1)）+ 只读 `PAGE_FIRST=1500` 行；`extend_photos()` 在空闲帧按 `PAGE_STEP=4000` 一页页补齐；`photos_total` / `photos_complete` 字段替代 `photos.len()` 给界面 | 5 万行一次 `LIMIT 200_000` 读进内存实测 **278 ms**，首屏卡死。分页后首屏查询 **4.56 ms**（release，`c_bench` 实测） |
| 5 | §2.1「栅格虚拟化」 | `GridLayout::build` 每帧重算（含 `group_by_day` 时区换算）——5 万张 **110 ms/帧**。加 `GridCache`：photos 没变直接返回（0 代价），尾部变长只 `extend()` 增量追加（O(新增量)），否则全量重建 | 滚动时输入几乎每帧相同，却每帧重算 110 ms，等于滚动即卡顿。`Cache` 之后每帧布局代价降为 0；仅首屏页时 `group_by_day` 0.14 ms、布局 0.12 ms |
| 6 | §2.1「栅格虚拟化」「日期分组」 | `group_by_day` 改写：同组第一张算一次 `NaiveDate` 作基准，后续逐张先走**整数相等快路径**（`other == ts`），再退化到时区换算比较 | 原实现每张都 `Local.timestamp_opt(...).single().format(...)` 再字符串比较，5 万张 ≈ 5 万次时区换算 + 字符串分配。整数快路径覆盖连拍/同秒导入（最常见），剩下才走换算 |

**关键环境坑（必须记下来，否则下次还会踩）**

- ⚠️ **`PRAGMA table_info` 不列出生成列**。探测 `eff_taken_at` 是否存在必须改用 `PRAGMA table_xinfo`
  （生成列在 `table_info` 里 `hidden=2` 被隐藏）。一开始用 `table_info` 探测 → 永远 false →
  所有连接都走 COALESCE 降级分支 → 索引建了也用不上，排序每次全表扫。这条是用

- ⚠️ **rusqlite 捆绑 SQLite 3.54.1**，比系统 python 的 3.50.4 新。新版计划器对
  `JOIN ... ORDER BY 生成列 ... LIMIT` 选边不同，不能拿 python 的执行计划当结论，必须用
  捆绑版本的源码编一个小工具（见 `target/` 外 `c_bench` 思路）实地验证。

**这一批的核心不是「把功能补齐」，而是把四个「看起来已经好了、其实没生效」的地方钉死。**

| # | 规划写法 | 实际落地 | 为什么 |
| --- | --- | --- | --- |
| 1 | §2.1「分批插入与可见区域锚定」 | 重载前记**照片 id**，重载后按 id 换算新 `y` 滚回去（`layout.thumb_rect(idx)` 反推偏移），**不用像素 offset** | 扫描会把新照片插到列表任意位置，旧的像素 offset 指向的已经是另一张图。只有 id 是稳定的；像素 offset 在「扫描刚导入了 200 张」时必然错位 |
| 2 | §2.1「大图逐级加载」 | 查看器先画**栅格里已有的 T0 缩略图**（512）当占位，2560 大图解码完成后再换；两者都没有才显示「正在解码…」 | 打开大图原本有 200~400 ms 的黑屏。而这张图的 512 缩略图**此刻就在显存里**（用户就是从栅格点进来的），拿它当 preview 是零成本，不需要额外解码路径 |
| 3 | §1.5「排除判定」只写在数据层 | 排除规则**在扫描遍历时**生效（`walk_and_store` 对每个目录 `exclusion.hits()` → `skip_current_dir()`），同时在树里隐藏 | 只在树里隐藏是**假修复**：下次扫描照样把照片重新灌进库，用户看到的是「关了又自己冒出来」。判定必须在写入端 |
| 4 | §2.1「右键刷新与任务合并去重」 | `Inner.queued: Mutex<HashSet<String>>` 记「排队中」的路径，`enqueue_refresh` 命中即返回 `false`；**worker 取走任务时 `q.remove(&key)`** | 只加不删会让长任务期间该文件夹**永远无法再刷新**（一次大目录索引跑 5 分钟，这 5 分钟里右键刷新全部被吞掉）。必须区分「排队中」与「已在跑」，后者靠 `board.task_by_path` 判 |
| 5 | §2.1「关闭根目录与重新添加复用」 | `roots.state`：0=active / 1=closed。**「关闭关注文件夹」只改状态、不删数据**，「从图库移除」才删索引。两者在右键菜单里是**两个独立项**，文案必须区分 | 用户点「关闭」的意图是「别再显示了」，删掉索引意味着下次重开要重新扫 5 分钟。重开复用同一个 `root_id`，索引与缩略图都还在 |
| 6 | §2.1「缓存空间显示与清理含 VACUUM」 | `clear_all_thumbs()` 删 `thumbs` 行的同时**必须 `UPDATE photos SET thumb_state = 0`**；`vacuum()` 先 `PRAGMA wal_checkpoint(TRUNCATE)` 再 `VACUUM` | ① 不清 `thumb_state` 的话，调度器认为「这张已经生成过了」，**永远不再重建**，缩略图从此全空；② WAL 模式下 `VACUUM` 的空间回收落到 WAL 文件里，用户看到「占用没降」，必须先 checkpoint 截断 |
| 7 | §2.1「已完成项自动收起」 | `IndexProgressPanel.show_completed` 默认 `false`，终态且无失败时才不画已完成分组，面板里留「已完成 N 项（点击展开/收起）」 | 索引跑完后面板被几十条「已完成」撑满，真正要看的失败项被挤出视野 |
| 8 | §2.1「诊断页」 | `DiagData` 汇总根目录状态 / 排除规则 / 缓存占用 / 失败清单，动作收成 `DiagAction` 枚举（ClearThumbs / Vacuum / RebuildAll / RestoreExclusion / ReopenRoot / Refresh），`apply_diag_action` 统一执行并把失败反成 `DiagFailure` | 以前这些只能靠看日志。诊断页的价值是**把「恢复」也做成一键**——只报错不给出口，用户还是只能重装 |

**G 的额外收益：`c_bench` 从「跑分工具」变成「门禁」**

- 阈值：首屏分页 ≤ 60 ms、每帧三件（分组+布局+可见区间）≤ 4 ms、全量 `group_by_day` ≤ 5 ms，
  外加 `TC-M21-PERF-001` 的**执行计划硬断言**（必须含 `idx_photos_eff_taken`、不得含 `TEMP B-TREE`）。
  超阈值 `exit(1)`，`--no-check` 只报告不判定。
- ⚠️ **判据项必须 best-of-N 采样，不能单次取值**。这台机器是 5 W 无风扇的 i5-8200Y，
  造完 20 万行索引库后已在降频区间：同一个「同一页 1500 行」的分组操作实测能在
  **0.96 ms 与 6.33 ms** 之间跳——输入规模完全一样。单次取值让门禁随机飘红，
  测出来的是「刚被热过的 CPU」而不是代码能力。改成 best-of-5 取最小值后稳定在 0.10~0.14 ms。
  回归会把最小值一起推高，噪声只推高峰值。
- 阈值只对标准规模（5 万张）有约束力：`group_by_day` 是 O(n) 的，20 万张 9.2 ms 属正常，
  所以非标准规模下该条 **SKIP 而非 FAIL**；而首屏分页与每帧三件是 O(页大小) 的，
  本来就该与总数无关——它们在任何规模下都判定。

**实测（release，5 万 / 20 万张）**

| 规模 | 首屏分页 | 分页追加一批 | 每帧三件 | 全量 `group_by_day` |
| --- | --- | --- | --- | --- |
| 5 万 | 2.1 ~ 3.5 ms | 6.5 ~ 7.3 ms | 0.10 ms | 2.2 ms |
| 20 万 | 3.1 ms | 6.8 ms | 0.14 ms | 9.2 ms |
| 对照：一次读全量（5 万） | **124 ms** | — | — | — |

首屏与每帧三件在 4 倍数据量下基本不动，全量分组按 4 倍线性增长——这正是分页要的效果。

**关键环境坑**

- ⚠️ **`IndexBoard::finish()` 在「全部终态且无失败」时会把任务列表整个清空**。测试里等终态
  如果只写 `task_by_path(&key).unwrap().state.is_terminal()`，会在这时拿到 `None` 直接 panic，
  或者永远等不到。正确写法是「`!snap.running()` 且（任务终态 **或** 任务不存在）——
  列表被清空同样等于全部完成」。
- ⚠️ **`walkdir::DirEntry::path()` 返回的是 `&Path` 而不是 `PathBuf`**。多写一次 `to_path_buf()`
  会被 clippy 报 `unnecessary_to_owned`，改成 `&entry.path()` 则变成 `&&Path` 触发
  `needless_borrow`，再改成 `.as_path()` 会解析到未稳定的 `str::as_str` 直接编译失败。
  直接传 `entry.path()`。
- ⚠️ **子智能体 shell 不继承工作目录**：所有 `cargo` 命令都要显式 `cd <仓库根> &&`，
  否则报「不是 Git 仓库」或输出为空。

## 3. 关键路径与风险

| M2 延期缺陷超出 3 人天预留 | 中 | **迭代 1 第一周内冻结清单**，超出部分进 M2.2，不占迭代 4 |

### 4.2 M3：布局与浏览

- **瀑布流排版**：直接读 `display_width` / `display_height`（生成列），无需重扫。
- **递归显示开关**：选中节点显示该目录及所有**未关闭**子目录的照片。排除在递归查询里的生效方式需在 M3 补查询设计（当前 `photos(folder_ids: &[i64], SortSpec, limit)` 已接受多目录，扩展点够用）。
- **递归计数**：在 `folders` 上增量维护**两列**——`total`（物理，P-07）与 `visible`（扣除已关闭子树）。
- **布局切换**：方格 ↔ 瀑布流，切换后保持浏览位置。

**已登记的验收项**

- 用"从 M2.1 升级、**回填尚未完成**"的库验证：宽高缺失的照片以默认比例占位，回填完成后自动重排为正确比例，**可见区域不跳动**。
- 递归显示 × 宽高占位 × 瀑布流三者组合的性能基准。
- 递归显示时，已关闭子目录的照片不出现，且 `visible` 计数与之相符。

### 4.3 M4：非破坏性编辑

- 旋转、裁剪、曝光与色彩等基础调整。
- **编辑参数只存应用数据库**，原图不动，导出生成新文件。
- 旋转基于 `orientation` 叠加计算，不重新解码原图。

**需提前决策（P-08）**：M2 起确立"照片目录零写入"。若允许写回原文件或生成边车 XMP，会直接击穿 `R-M2-1` 与 `docs/03` 的 `TC-RO` 只读用例。**建议维持零写入，只导出**；这一点在 M3 中期前确认即可，但它决定 M3 期间是否预留编辑数据表。

### 4.4 M5：检索与整理

- 按日期、相机型号、尺寸、方向、文件类型筛选。
- 文件名与路径搜索。
- 收藏与标签，同样只存应用数据库。

宽高与方向在 M2.1 已入库，M5 的尺寸/方向筛选可直接用。**相机型号等其他 EXIF 字段需要在 M3 或 M4 的回填中顺带补齐**，避免 M5 再做一次全量回填——这一条是排期上的硬约束，不是优化项。

### 4.5 跨版本数据库演进

| 版本 | 数据库变更 | 迁移版本 |
| --- | --- | --- |
| M2.1 | `roots` 表、`folders` 层级、`dims_status` + 生成列、排除表、任务与失败表 | **v2** |
| M3 | `folders` 递归计数双列、布局偏好 | v3 |
| M4 | 编辑参数表 | v4 |
| M5 | 扩展 EXIF 字段、标签与收藏表、搜索索引 | v5 |

每个版本沿用 M2.1 的迁移框架：判定 `schema_version` → `VACUUM INTO` 备份 → 单事务 DDL → 幂等补数 → 失败回滚。**只增不改、不跨版本跳跃**（v2 → v4 必须经 v3）。

## 5. 待确认（P 续编自 `04` §7）

| 编号 | 问题 | 状态 | 建议 / 结论 |
| --- | --- | --- | --- |
| ~~**P-07**~~ ✅ | 关闭子目录后，其照片是否计入父目录计数 | **已裁决** | `direct_count` 是物理事实，不随关闭变化；M3 递归计数拆 `total` / `visible` 两列。理由：一个数承载两种语义，后面必然对不上（见 §1.3.3） |
| **P-08** | M4 是否坚持照片目录零写入（只导出、不写回、不出边车 XMP） | **待确认** | **建议坚持零写入**。边车 XMP 会击穿 `R-M2-1` 与 `TC-RO` 全部只读用例，收益远小于破坏。M3 中期前拍板 |
| **P-09** | M4（编辑）与 M5（检索）是否调换顺序 | **待确认** | **建议维持 M4 在前**。`orientation` / `display_*` 在 M2.1 就位后，编辑的数据基础已完成大半；而 M5 还欠一次 EXIF 全量回填，先做 M4 可把这次回填摊进 M3/M4 |
| **P-10** | 团队配置与 M2 延期 P1 清单 | **待确认** | 工时按 2 开发 + 1 测试估。清单请在**迭代 1 第一周内冻结**，超出 3 人天的进 M2.2 |

**由此确定的三件事**

1. **`roots` 只能有一个真相源**：迁进 DB 之后，`Preferences.roots` 降级为只读兼容字段；任何"再加一个根目录"的路径都必须走 DB。
2. **迁移只前不退**：`SchemaTooNew` 守卫不放宽，降级靠备份覆盖，写进用户可见的提示。
3. **EXIF 回填一次做完**：M3/M4 的回填顺带补齐相机型号等字段，M5 不再全量重扫。
