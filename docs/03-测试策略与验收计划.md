## 变更横幅（v2.0）：不做 Picasa 兼容，做一个新程序

> **用户新决策（覆盖此前所有 ini 相关要求）**：
> 「**不需要读和写 picasa.ini，是做一个新的程序。**」
>
> 这不是又一次缩范围，而是**立场变更**：从"复刻 Picasa 的数据格式"变成"**做一个自己的程序，只是界面像 Picasa**"。
>
> | 维度 | v1.0（兼容路线） | **v2.0（自立路线）** |
> |---|---|---|
> | `.picasa.ini` | 只读、原样保留、绝不写 | **完全不读、完全不写**（不存在该文件的概念） |
> | 星标/说明/编辑历史 | 读取并只读展示 | **不读取、不展示**（没有数据源） |
> | 数据模型 | 复用 Picasa 的 ini + 自家索引 | **完全自立**：自有 SQLite + 自有偏好，只在应用容器 |
> | 核心安全命题 | `.picasa.ini` 零写入 | **「照片目录零写入」**（更强、更简单、更好测） |
>
> ### 对测试侧的三点影响
>
> **① 减负（21 条用例 + 若干章节前提消除）**：所有 ini 内容/格式/字节相关用例**前提消失**——不兼容就无从对拍。
> **② 加强（命题升级）**：从"盯一个文件"变成"盯整个目录"。**断言更强但更好写**，这是好事。
> **③ 新增（自立带来的新要求）**：自有数据模型的正确性成为新测试面（§5D）——缓存被删、SQLite 损坏、偏好丢失、schema 变更。
>
> ### 新增第四类用例状态：`前提消除`
>
> | 状态 | 含义 | 与"永久废弃"的区别 |
> |---|---|---|
> | **`前提消除`** | 该用例的**验证前提已不存在**（不再兼容原版 ini），因此用例本身失去意义 | "永久废弃"是产品决定不做某项**功能**；"前提消除"是**功能可能还在，但原本的验证手段失效**。例如编辑功能 M2 仍会做，但"ini 序列化往返"这个测法永远用不上了 |

## 变更横幅：M1 定义被推翻重写（必读）

> **v1.0 是一次破坏性重构，不是增量修订。** 用户（产品所有者）推翻了旧 M1 定义。
>
> | | 旧 M1（v0.1~v0.4）**已作废** | 新 M1（v1.0，当前有效） |
> |---|---|---|
> | **定位** | 图库 + 查看器 + **非破坏性编辑内核** + 性能红线 | **界面复刻 + 浏览**（可在 M 系列 Mac 上安装运行的 `.app`） |
> | 第一优先级 | 编辑正确性（像素对拍、ini 双向兼容） | **界面还原度** |
> | 编辑功能 | 核心（F3 全域 + 编辑内核） | **全部移出 M1**（F3 全 52 条）；唯一保留 EXIF Orientation 自动摆正 |
> | `.picasa.ini` | 双向读写 | **严格只读，绝不写**（Lead 硬约束） |
> | 平台 | macOS/Windows/Linux 三平台 | **仅 macOS 14+ / arm64** |
> | 交付形态 | 未定 | **本地 `.app` + ad-hoc 签名**，不公证 |
>
> **测试重心随之四块转移**：① **界面还原度**（新第一优先级）② **浏览正确性与性能** ③ **macOS 安装与运行**（打包/签名/Gatekeeper/TCC）④ **数据只读安全**（不得写坏 ini）。
>
> **旧内容的处理**：旧 M1 的测试设计**一律不删**，逐处标注 **「旧 M1（编辑优先），已作废」** 并保留——这是决策线索，删了就没人知道为什么现在不测编辑了。相应用例保留原编号，状态改为 **「M2 恢复」**。

### 用例状态标记体系（贯穿全文；v2.2 起五类）

| 状态 | 含义 | 处理 |
|---|---|---|
| **`M1 有效`** | 新 M1 范围内，M1 阶段必须通过 | 计入 M1 门禁 |
| **`M2 恢复`** | 功能移出 M1 但**未废弃**，M2 起重新生效 | 保留编号与设计，M1 不判失败 |
| **`前提消除`** | 用例所依赖的判据已不存在（不读不写 `.picasa.ini` ⇒ ini 兼容/对拍类判据消失）。**不是废弃**，登记见 §11.16 | 不计入任何门禁分母 |
| **`M2 新增`** | **v2.2 新增分类**：M2 才出现的新范围（当前只有 §11.18 索引进度可见性 24 条）。与 `M2 恢复` 的区别是**无历史编号可恢复**，属全新设计 | 计入 M2 门禁；M1 阶段不判定 |
| **`永久废弃`** | 因范围变更**永远不会再做**。**当前计数为 0**——凡"平台延迟"或"M2 再做"都不属于此类 | 保留该状态定义以备将来使用；误用会被视为分类错误 |

本文档的核心命题是回答一个问题：

> **"1:1 复刻" 怎么证明？**

答案不是"功能都能点开"，而是三条可机器判定的证据链：

1. **像素证据**：同样的输入图片 + 同样的编辑指令，输出与基准的差异在声明容差内。
2. **数据证据**：`.picasa.ini` 读写与原版 Picasa 3.9 双向互通，且不破坏用户既有数据。
3. **行为证据**：关键用户旅程的交互路径、快捷键、状态迁移与原版一致。

## 1. 测试原则

### 1.1 五条硬原则

1. **原文件永不修改**（对应非破坏性编辑模型）。任何测试读到原图，必须在用例前后比对 `size + mtime + SHA-256` 三元组，不一致即用例失败——这条优先级高于功能正确性。
2. **先测破坏面，再测功能面**。删除、批量重命名、移动、备份恢复、写 ini 是最容易造成用户数据损失的路径，必须先有测试再写实现。
3. **兼容性测试数据必须外部来源，禁止自产自测**。用我们自己的解析器写出的样本，再用来测我们自己的解析器，是无效测试。原版样本必须由真机 Picasa 3.9 产出并冻结入库。
4. **性能红线用 p95/p99，不用平均值**。平均值会掩盖缩略图栅格偶发的长帧，而长帧正是用户能感知到的卡顿。
5. **每个用例都必须能"预期失败"**。用例写在实现之前，先红后绿；不能写出一个永远为真的断言。

### 1.2 测试金字塔比例（目标）

| 层级 | 数量占比 | 运行时长预算 | 触发时机 |
|---|---|---|---|
| 单元 | ~70% | < 60s | 每次保存 / pre-commit |
| 集成 | ~20% | < 5min | 每次 push / PR |
| 端到端 + 截图回归 | ~8% | < 15min | PR + nightly |
| 性能 + 模糊 + 长稳 | ~2% | 小时级 | nightly / 发版前 |

> 反模式警告：不要用端到端测试覆盖本该单元测试的逻辑。GUI 端到端用例应只覆盖"旅程"（跨 3 个以上模块的路径），单点逻辑缺陷必须能在单元层被抓住。

### 2.2 单元测试

**重点覆盖"纯函数 + 边界"**，这是性价比最高的一层。

- **图像算法**：以"数学性质"而非"像素相等"做主要断言，像素相等仅作回归快照。
  - 可逆性：`rotate(90)×4 == identity`；`crop` 后再 `crop` 等价于一次 `crop` 的并集。
  - 恒等性：参数为中位值时变换近似恒等（亮度/对比度/饱和度 0 点）。
  - 单调性：亮度参数递增 → 平均亮度单调不减（容差内）。
  - 幂等性：`autocontrast` 连续两次 == 一次（容差内）。
  - 边界：1×1、1×100000、全黑、全白、单通道、带 alpha 全透明。
- **`.picasa.ini` 解析器**：见 §5 矩阵，要求行覆盖率 ≥ 95%、分支 ≥ 90%。
- **路径处理**：这是跨平台 Bug 高发区，必须独立成组。
  - Windows 盘符、UNC 路径 `\\server\share`、`\\?\` 长路径前缀。
  - macOS/Linux 的符号链接、`..` 逃逸、尾随分隔符。
  - Unicode NFC/NFD 归一化（macOS HFS+/APFS 的 NFD 陷阱）。
  - GBK / Shift-JIS 文件名（Windows 遗留库）、UTF-8 带代理对（emoji）。
  - 大小写不敏感 vs 敏感的同一路径去重。
  - 非法字符、路径长度 > 260 / > 4096、空路径、`.` `..` 单独作为根。

**测试组织约定**：

- 内联单测放在 `src/**/tests.rs` 或 `#[cfg(test)] mod tests`。
- 需要 fixture 的集成测试放各 crate 的 `tests/`。
- **重测试必须打标记**：`#[ignore = "heavy: 需要 100k 数据集"]`，由 CI 显式 `--ignored` 拉起，避免本地 `cargo test` 卡死。
- 测试必须**并行安全**：任何写磁盘的用例使用独立 `tempfile::TempDir`，禁止共享固定路径；禁止依赖执行顺序。

#### 3.5.1 版本化与冻结规则

| 项 | 规则 |
|---|---|
| 当前版本 | **`face-set-v1`**（本节首次定稿即冻结） |
| 版本号语义 | `face-set-v<major>`。**major 递增 = 验收基线变更**，必须重新评审 90%/5% 阈值，并在里程碑记录中注明"因样本集变更导致指标不可比" |
| 冻结方式 | 集合目录 `testdata/face-set-v1/` + `face-set-v1.manifest.toml`（逐文件 sha256） |
| **集合哈希** | `face_set_hash = sha256(按路径排序后逐行 "相对路径:sha256\n" 的拼接)`，记录在 manifest 头部与 03 文档。**任何一张图增删改都会改变该哈希** |
| 变更纪律 | 冻结后**禁止原地替换**；只能新建 `face-set-v2/`。v1 永久保留用于历史回归，否则"上一版 92%、这一版 89%"无法判定是模型退化还是样本变难 |

#### 3.5.3 三个指标的精确定义（必须写死，否则口径可被操纵）

**指标 1：检出率（Recall）**

```
Recall = TP / (TP + FN)
```

| 术语 | 精确定义 |
|---|---|
| **真阳性 TP** | 预测框与标注框 **IoU ≥ 0.5**，且**一对一匹配**（一个预测框只能算一次命中） |
| **假阴性 FN** | 存在标注框，但没有任何预测框与其 IoU ≥ 0.5 |
| **计入分母的范围** | **仅 L1 正脸层**（40 张 / 40 张脸）。这是 01 原文"检出率 ≥90%（正脸）"的直接落地 |
| **不计入分母** | L2 侧脸、L3 墨镜、L4 遮挡、L5 低光、L7 多样性组 —— 这些**允许漏检**，单独出报告供参考，不参与 90% 判定 |
| 多人图（L6） | 逐脸匹配，一张 8 人图里漏 1 张算 1 个 FN，按脸计数而非按张计数 |
| 阈值 | **≥ 90%**（在 L1 上）。L1 只有 40 个实例，**每漏 1 张 ≈ 降 2.5%**，故允许最大漏检 4 张 |

**指标 2：误检率（False Positive Rate）**

> **口径要点**：分子与分母必须同为"框级"或同为"图级"，混算会让指标失去意义。此处统一采用**框级（detection-level）**口径。

```
FPR = 全部假阳性框数 / (全部预测框数)
    = FP / (TP + FP)          ← 精确率意义上的 1 - Precision
```

| 术语 | 精确定义 |
|---|---|
| **假阳性框 FP** | 预测框与**该图全部标注框**的 IoU 均 < 0.5（即"框出了一个不存在的人脸"） |
| **分母** | **全部预测框**（正例图的 + 负样本图的），因此负样本图的每一个预测框都直接计入分母且全部为 FP |
| **为什么用框级** | 图级口径下"一张 8 人图里框错 1 个"与"一张单人图框错 1 个"权重相同，会稀释多人图的误检；框级更贴近用户实际感知 |
| 排除项 | 同一张脸被框两次（**IoU ≥ 0.3 的重复框**）**不算 FP**，归入指标 3 的"重复框"类别 |
| 阈值 | **≤ 5%**（即精确率 ≥ 95%）。**负样本层必须保留 10 张**：若模型在负样本上乱框，分母里的 FP 会快速堆积，指标立刻恶化——这正是该层的作用 |
| 附报指标（非门禁） | 同时报出**负样本误检图数/10**（图级），便于观察"整张图被误判"的严重情况；此项仅作参考，不参与 5% 判定 |

> 注意：v0.3 初稿曾写 `FPR = FP/(FP+TN)` 且把"10 张负样本图"当 TN、把"框级 FP"当分子——**分子框级、分母图级，量纲不一致**，会让 5% 无法解释。已修正为上面的框级口径。

**指标 3：拆脸率（Split-Face Rate）** —— 对应 01 的"不得把一张脸拆成多人"

```
SplitRate = 被拆分的标注脸数 / 全部被检出的标注脸数
```

| 术语 | 精确定义 |
|---|---|
| **一张脸被"拆成多人"** | 同一个标注脸对应 **≥2 个预测框**，且这些框彼此 **IoU < 0.3**（即不是同一区域的重复框，而是分裂成相邻两块，如把左眼+鼻子和嘴部各框一个）。这些框里 IoU 最高的那个记为 TP，**其余全部记为"拆脸"** |
| 与重复框的区别 | 两框 **IoU ≥ 0.3** 视为"同一张脸的重复检测"，只算 1 次 TP、不记拆脸（属后处理 NMS 可合并的正常现象） |
| 分母 | 全部被检出的标注脸（跨所有正例层，含侧脸/遮挡层，因为拆脸在低质量脸上更易发生） |
| 阈值 | **= 0**（v1 阶段要求零容忍）。这是 01 的硬要求"不得拆成多人"，不是百分比指标 |
| 报告要求 | 每次必须列出**拆脸的具体样本 ID 与拆分框坐标**，便于定位是检测问题还是 NMS 参数问题 |

#### 3.5.4 断网执行要求（F10-07 / F5-06 联动，强制）

01 已明确人脸检测"**运行期不联网、模型内嵌**"。因此：

| 要求 | 做法 | 判定 |
|---|---|---|
| **测试环境必须物理/逻辑断网** | 关闭 Wi-Fi 与有线网络，或防火墙默认拒绝全部出站 | 断网后测试能否**跑起来**本身就是一个用例（模型内嵌则能跑） |
| **禁止首次运行联网下载模型** | 干净环境首次启动即断网 | 若因缺模型而失败 → **直接判 F10-07 不通过**，即使精度达标 |
| 禁止用"联网下载后才达标"的结果 | 报告须记录测试时的网络状态 | 联网状态下跑出的精度**不予采信** |
| 安装包体积核查 | 模型内嵌 → 安装包体积须含模型 | F10-07 ④ 允许基线 +20MB；超限需重新评审 |

> 这条的本质是：**如果模型靠网络下载，那"断网可用"的承诺就是假的，而精度测试还会因为网络顺畅而掩盖它**。测试必须先把网络这个变量钉死，再谈精度。

## 4. 像素级对拍（Pixel Diff）策略

### 4.1 核心难点

原版 Picasa 是闭源 Windows 应用，**其内部算子实现不可得**，且部分效果依赖当时特定的像素插值/CUDA 行为。因此"逐像素完全相等"在多数场景不可达，必须定义**分级容差**。

### 4.2 三级基准（Baseline Tier）

按可信度从高到低，优先使用高等级基准：

| 等级 | 基准来源 | 适用 | 容差 |
|---|---|---|---|
| **B1** | 原版 Picasa 3.9 在 Windows 实机（或虚拟机）上导出的结果图 | 编辑效果、导出、缩略图 | 按 §4.3 表 |
| **B2** | 公开规范/参考实现（如 libjpeg、lcms2、ImageMagick 加减速器） | 解码、色彩转换、几何变换 | 严格（几何 ±0/1px） |
| **B3** | 数学性质断言（可逆性、单调性、恒等性、幂等性） | 无法取得基准时兜底 | 性质级 |

**B1 的取得流程（一次性，产出即冻结）**：

1. 在干净 Windows 虚拟机安装 Picasa 3.9（官方最终版）。
2. 每张基准样本执行**单一操作**（只调一个参数），导出为 PNG（避免二次 JPEG 损失）。
3. 记录操作参数、Picasa 版本、Windows 版本、显卡无关的软件渲染设置。
4. 产物入 `testdata/picasa-original/`，与 `manifest.toml` 绑定 sha256。
5. **禁止**用"我们自己的输出"回填 B1。

> 若 B1 在项目周期内无法取得（法务/环境限制），必须在里程碑评审时显式降级为 B2+B3，并在 §13 风险表登记"1:1 像素级复刻不可证"的结论，不允许静默假设。

### 4.3 容差分级表

| 操作类别 | 判定指标 | 阈值 | 说明 |
|---|---|---|---|
| **无损几何**（rotate 90/180/270、flip、crop、transpose） | 最大通道绝对差 | **0**（严格逐像素相等） | 整像素搬运，无插值，无理由不等 |
| 几何的坐标断言 | 矩形坐标差 | **≤ 1 px** | 边界取整差异可接受 |
| **缩放/重采样**（缩略图、导出 resize、拉直） | PSNR / SSIM | **≥ 40 dB / ≥ 0.99** | 不同插值核会有微差 |
| **色彩/色调**（亮度、对比度、饱和度、色温、高光、补光） | PSNR / SSIM / ΔE2000 | ≥ 38 dB / ≥ 0.985 / mean ≤ 2.0, p99 ≤ 4.0 | 色调映射曲线可能略有差异 |
| **自动类**（自动对比度、自动色彩） | PSNR / SSIM | ≥ 32 dB / ≥ 0.97 | 直方图统计口径差异 |
| **效果滤镜**（黑白、复古、颗粒、渐晕、素描、油画等） | PSNR / SSIM / ΔE2000 | ≥ 32 dB / ≥ 0.97 / mean ≤ 3.0 | 颗粒/噪声类可额外放宽 p99 ΔE ≤ 8 |
| **随机类效果**（胶片颗粒） | 统计量等价 | 均值差 ≤ 1/255、标准差差 ≤ 5% | 固定 seed 后仍以统计量判定，不逐像素 |
| **JPEG 编码输出** | 解码后 PSNR | ≥ 42 dB | 编码器实现差异 |
| **锐化** | 边缘过冲 | overshoot ≤ 5% 动态范围 | 防止光晕（halo）为视觉缺陷 |

### 4.4 指标定义（实现约定）

- **PSNR**：按通道计算后取最小值（最差通道），而不是全图平均——平均会掩盖单通道崩坏。
- **SSIM**：11×11 高斯窗，σ=1.5，标准实现；对带 alpha 图先做 alpha 合成到黑/白背景各算一次。
- **ΔE2000**：需先把两边转到 CIELAB（D65，sRGB 输入按 lcms2 处理 ICC）。
- **比较前必须做的归一化**：统一位深到 8bit（除特批用例）、统一到 sRGB 显示空间、alpha 预乘策略一致。**不做归一化直接比是无效对比**。

### 4.5 对拍报告

每次对拍产出机器可读报告，供回归趋势追踪：

```jsonc
{
  "run_id": "2026-10-27T14:00:00Z",
  "sample": "syn-003-exif-orientation.jpg",
  "op": "rotate:90",
  "baseline_tier": "B1",
  "metrics": { "max_channel_diff": 0, "psnr_min": 99.0, "ssim": 1.0, "delta_e2000_mean": 0.0 },
  "threshold": { "max_channel_diff": 0 },
  "verdict": "pass",
  "diff_image": "reports/diff/syn-003-rotate90.png"
}
```

视觉化：差异图用**放大 32 倍的差值热图** + 并排三联图（基准 / 实际 / 差值）。人眼复核只需看热图即可定位区域。

## 5. `.picasa.ini` 双向兼容测试矩阵

这是"1:1"最硬的证据，也是最容易毁用户数据的地方。

### 5.1 真实键名分组（已按原版样本校准）

> **v0.2 修订说明**：v0.1 曾假设存在 `rotate=`、`filter_xxx=`、`[.album:名称]` 段，经 PM 依据原版逆向资料与真实样本核对，**这三处均为错误假设，已删除**。
> 字段全量以 `02-技术架构与选型.md` 的兼容契约表为准；若 02 与本节冲突，先核对原版样本再定，**不允许两处各写一套**。

`.picasa.ini` 的实际形态是 **`[Picasa]` 段（全局/相册级）+ 以照片文件名为段名的单图段**，而不是"每个相册一个段"。

| 分组 | 真实键 | 格式与语义 | 测试关注点 |
|---|---|---|---|
| 星标 | `star` | `star=yes`（**两态：加星/未加星，原版无 1–5 星**） | 缺失 vs `star=yes`；`star=no` 是否等价于缺失 |
| 说明 | `caption` | 自由文本，可含换行 | 非 ASCII、emoji、超长、换行转义 |
| 关键词 | `keywords` | `keywords=a,b,c` 逗号分隔 | 逗号在标签内的转义、空标签、顺序保留 |
| 相册归属 | `[Picasa]` 段内 `name=` / `category=` | 相册名与分类**写在该目录 ini 的 `[Picasa]` 段**；成员关系在用户目录数据库 | 中文相册名、重名、跨目录同名相册合并 |
| 单图段名 | `[<照片文件名>]` | 以文件名作 section 名 | **NFC/NFD、中文/日文/emoji 文件名能否匹配**、大小写 |
| 几何-裁切 | `crop64` | `crop64=1,<rect64>`；`rect64(...)` 为 16 位十六进制拆 4 段再 /65536 得相对坐标（**左,上,右,下**） | 坐标顺序、`/65536` 精度、旋转后坐标系、边界 0/65536 |
| 几何-旋转/拉直 | **不存在 `rotate` 键** | 旋转与拉直由 `filters` 内的 `crop64`/`tilt` 组合表达 | 与 EXIF Orientation 的叠加顺序（谁先谁后） |
| 效果 | `filters` | **单键承载全部效果**，分号分隔多条指令：`id=1,参数1,参数2;`，如 `enhance=1;autolight=1;sepia=1;sat=1,0.161800;` | **多指令顺序必须保持**、**6 位浮点精度往返**、**未知 `id` 原样保留**、空参数、尾部分号 |
| 人物 | `[Contacts]` 段 | 人物名映射 | 与人名段冲突、重名合并 |
| 未知 | 任意未识别键/段 | — | **必须原样保留且保持顺序**（写回逐字节不变） |

**由上述事实直接导出的四条硬性测试要求**（v0.1 缺失第 1~3 条，第 4 条来自 02 §5.3 的关键提醒）：

1. **`filters` 是有序指令串，序列化必须保序**——顺序变了效果就变了（`enhance` 在 `sepia` 之前与之后结果不同）。因此 §2.3 的"往返"断言必须是**字符串级有序相等**，不是集合相等。
2. **浮点参数固定 6 位小数**：`0.161800` 往返后不能退化成 `0.1618` 或 `0.16179999`。解析与格式化必须互逆，这一条足以让大量"看起来能读"的实现翻车。
3. **`rect64` 的十六进制 4 段拆分与 `/65536` 相对坐标必须双向可逆**。裁切精度用例要做 `crop → 序列化 → 反序列化 → 再裁切`。
4. **⚠️ `÷65536` 是不可逆的，所以"坐标差 ≤ 1/65536"这个容差本身就是错的判据**（02 §5.3 明确指出：`from_norm(to_norm(x))` 因四舍五入会偏移 1 个 LSB）。正确判据是：
   - **实现必须保存原始 4 个 `u16`**（`Rect64 { l,t,r,b: u16 }`），而不是 f32 归一化值；
   - 因此往返断言应为 **`to_hex(parse_hex(s)) == s` 逐字符完全相等（零容差）**，而不是"数值近似"。
   - 一旦某实现在内部转 f32 再写回，就会出现 ±1 LSB 漂移，**直接导致 RT-01 的逐字节对比失败**——这正是这条用例要抓的缺陷。**允许 1/65536 容差等于把该缺陷放行为"通过"。**

> 02 §5.4 对 `filters` 给了同构建议：`RawFilter { raw: String, id, params }` 保留原始字符串用于写回，只在计算时解析 `params`。**测试侧对应要求：任何"解析成结构体再拼回"的实现都必须在 RT-04~RT-08 上被判定为失败，即便语义等价**——因为语义等价换不回字节等价，而字节不等价会破坏原版互操作与 git/同步盘的 diff 稳定性。

## 5A. 界面还原度测试（新 M1 第一优先级）

> **为什么单独立一章**：M1 的定位已从"编辑正确"变成"**看起来就是 Picasa**"。界面还原度成了交付的第一验收项，但它恰恰是最容易滑向"人眼看差不多"的地方。本章的唯一目标是把"像不像"转成**可复现、可争论、可签字**的数字。

### 5A.1 先说不做什么：为什么不能用 SSIM 当主判据

这是本章最重要的判断，必须写在最前面：

| 做法 | 为什么不行 |
|---|---|
| **用 SSIM/PSNR 做主判据** | 界面截图里文字占很大面积，而 **macOS 与 Windows 的字体栅格化（hinting、subpixel AA、stem darkening）本质不同**。同一份布局、同一字号，SSIM 也可能只有 0.85~0.92。此时 SSIM 的"合格线"要么定得极低（失去判别力），要么定得高到永远不过（团队学会忽略它）。**两种结局都让门禁失效。** |
| **纯人眼评审** | 不可复现、不可争论、无法做回归。评审人换了结论就换。 |
| **逐像素 diff 占比** | 同上，被字体反锯齿噪声淹没，且对"整体右移 2px"这类真实缺陷反而不敏感（位移后每个像素都不同，占比 100%，但人眼看不出；反过来字体差异也 100%）。 |

**结论**：主判据用 **结构化几何量 + 配色量 + 精确像素边长**；**动态/文字密集区域**才用像素法（且必须遮罩）。SSIM 只作为**辅助趋势指标**记录，**不作为门禁**。

### 5A.2 三段式判据体系

| 判据类别 | 量 | 阈值 | 适用对象 |
|---|---|---|---|
| **G 几何** | 控件位置/尺寸偏差 | **≤ 2 px**（@1x 逻辑像素）；对齐线偏差 ≤ 1 px | 面板边界、工具栏、状态栏、单元格 |
| **G 几何（严格）** | 缩略图三档像素边长 | **必须精确相等，容差 0** | 栅格缩略图 |
| **C 配色** | 取色 HEX / ΔE2000 | 主色/选中色 **HEX 必须相等**；渐变与抗锯齿过渡区 **ΔE ≤ 3.0** | 背景、选中态、分组头、工具栏 |
| **T 排版** | 基线位置、行高、字距 | 文本块**包围盒**偏差 ≤ 2 px；**不比对字形像素** | 工具栏文案、文件名、状态栏 |
| **P 像素（受限）** | 遮罩后差异像素占比 | ≤ 0.5%，且无连通区域 > 64 px | 仅图标区、纯色区；**文字区必须遮罩** |

> **✅ 照片托盘位置：已定稿（01 v2.1 裁决）**——Photo Tray 位于**左侧栏最底部**，横向缩略图条，可展开/收起，不悬浮、不在右侧、不覆盖栅格。
> v2.0 需求初稿曾误写"右侧"，属按"常见看图软件惯例"想当然。**该争议已关闭**，本表 U-36 由 `BLOCKED` 转为可判定项；判据重点从"方位是哪边"改为"展开时左栏宽度不变、且不越界压栅格"。

> **关键**：`T 排版` 只比**包围盒**（文字从哪里开始、多高、多宽），不比字形。这样既抓住了"字号错了/位置错了/换行了"这些真缺陷，又完全免疫字体渲染差异。

### 5A.5 界面还原检查表模板（**严格对应 01 的 U-01~U-44，44 项**）

> **编号即契约**：本表编号 **U-01~U-44 与 `01-产品功能清单.md` §11.5.6 完全一一对应**——同一个编号指的是**同一个被测对象**，不是"数量恰好都是 44"。
> **分工**：01 定「要复刻成什么样」（定性目标）；本表定「怎么量、判多少」（可执行判据）。
> **纪律**：若 01 增删或重排 U 项，本表必须同步增删重排，**编号不允许错位**。错位比缺项更糟——验收时会出现"你说测了 U-21、我这边 U-21 是别的东西"。
>
> **填法**：`基准值` 来自 `ui-baseline.toml`；`实测值` 来自 `measured.toml`；`结论` 只有 **PASS / FAIL / BLOCKED** 三态。
> `BLOCKED` = 基准尚未取得（01 中标 ⚠️待核对的 26 项），**不计入通过率分子分母**。
>
> **判据代号**：`G` 几何（≤2px，缩略图边长零容差）｜`C` 配色（HEX 相等 / ΔE≤3.0）｜`T` 排版（只比包围盒，不比字形）｜`P` 像素（遮罩后 ≤0.5%）｜`B` 布尔（是/否）。

### 5A.6 三档缩略图真实像素值的实测方法（回答"数字从哪来"）

> 这是 PM 要在 01 里写死的数字。**没有可复现的量法，那个数字就是猜的。** 下面是唯一推荐方法，按顺序执行。

#### 方法：栅格间距法（推荐，精度最高）

**核心思路**：不要直接量单张缩略图的边界（抗锯齿/阴影/边框会让边界模糊 ±1~2 px），而是**量相邻两张缩略图的中心距**，再用间距公式反推边长——中心距是**亚像素稳定**的，且误差被平均掉。

```
步骤：
1. 准备一张全白/纯色测试图集（30 张纯色图，避免图片内容干扰边界识别）
2. 原版 Picasa 切到目标档位（小/中/大），加载图集，截图为 PNG（无损）
3. 在截图里找到栅格区，沿某一行取一条水平扫描线
4. 沿扫描线找"缩略图区域"与"背景间隙"的交替边界，得到
     - 第 i 张的左边界 L_i、右边界 R_i
5. 边长 D_i = R_i - L_i（对 30 张取中位数，剔除首尾）
6. 中心距 P_i = (L_{i+1} + R_{i+1})/2 - (L_i + R_i)/2
7. 水平间距 gap_h = P - D
8. 同理取垂直方向，得行高与垂直间距 gap_v
9. 用列数校验：floor((W_grid + gap_h) / (D + gap_h)) == 实测列数
    （若不等，说明边界识别有误，回第 4 步）
```

**判定与记录**：

| 输出 | 定义 | 容差 |
|---|---|---|
| `D_small` / `D_medium` / `D_large` | 三档缩略图边长（**逻辑像素**） | 30 张的中位数；**若 30 张中有任何一张的 D 与中位数差 > 1 px，判定该档位量测不可靠，需重测** |
| `gap_h` / `gap_v` | 水平/垂直间距 | ≤ 0.5 px 抖动视为一致 |
| @2x 校验 | 同一档位在 @2x 截图上量得的值**必须恰好是 @1x 的 2 倍** | 否则说明原版在 Retina 下并非整数倍渲染，需在 01 中注明 |

> ⚠️ **必须分清"逻辑像素"与"物理像素"**：原版是 Windows 程序，其"像素"是逻辑像素。在 macOS @2x 下截图得到的是物理像素。**写进 01 的规格必须是逻辑像素**，否则实现方在 Retina Mac 上会做出半个大小的缩略图。**这一步错了，整个界面还原的栅格密度就全错了。**

#### 方法 B：十字线法（交叉验证）

用截图工具的取色/坐标读数，在**最高倍（原始 @2x）**截图上放大到 800%，手动读取缩略图左右边缘坐标。用于**交叉验证方法 A**，两者差 > 2 px 时必须重测。

#### 方法 C：不可用的做法（明确排除）

| 做法 | 为什么排除 |
|---|---|
| 直接量"看起来的"一张图边长 | 边框/阴影/圆角让边界模糊，误差 ±2~3 px，足以让 85 与 88 分不清 |
| 从网上的评测文章截图量 | 经过二次缩放与 JPEG 压缩，像素已不可信 |
| 用 ACDSee/系统预览等第三方软件的"缩略图大小"设置去猜 | 各家定义不同（含/不含边框、是否含文件名区），不可迁移 |
| 按"看起来大概是 85/144/200"直接写死 | 这是**猜测而非测量**，且一旦写错，UI-26~28 的零容差判据会立刻全员失败，但没人知道是判据错还是实现错 |

## 5B. macOS 安装与运行测试（新 M1 的核心交付面）

### 5B.1 打包产物校验（不需要真的能跑，先验结构）

| # | 检查项 | 判据 | 判法 |
|---|---|---|---|
| PKG-01 | `.app` 是目录结构而非单文件 | `OpenPicasa.app/Contents/MacOS/` 存在 | `ls` / `find` |
| PKG-02 | 可执行文件存在且可执行 | 权限含 `x`，`file` 显示 `Mach-O 64-bit executable arm64` | `file`、`ls -l` |

### 5B.2 Gatekeeper 三条路径（**必须分开测，合并测等于没测**）

这是本章最容易被偷懒的地方。三条路径的**系统行为完全不同**，因为决定性变量是 **com.apple.quarantine 扩展属性**，而不是签名本身。

| 路径 | 场景 | quarantine 状态 | **预期行为** | 判据 |
|---|---|---|---|---|
| **G1 本机构建直跑** | 开发者在自己机器上 `cargo run` 或直接打开 `target/.../OpenPicasa.app` | **无** | **直接双击可运行**，无任何拦截 | 无弹窗、无"无法验证开发者" |
| **G2 U 盘/局域网拷贝到另一台 Mac** | 仅 U 盘、移动硬盘、`cp`、`scp` | **无**（`cp`/`scp` 不加 quarantine） | **直接双击可运行**，无任何拦截 | 无弹窗可运行 |
| **G3 从网上下载** | 浏览器下载、邮件附件、**AirDrop** | **有**（`0083;...;Safari;` 等） | **首次双击被拦**，提示"无法打开，因为无法验证开发者"；**必须右键→打开→再确认**才能运行；之后不再拦 | 弹窗文案正确、右键打开可绕过、二次打开不拦 |

**三条路径的独立判定表**（每条都要单独出结论）：

| 用例 | 预置条件 | 期望 | 反例（以下任一即失败） |
|---|---|---|---|
| G1 | 本机构建产物，`xattr -l` 无 quarantine | 双击即开 | 出现任何 Gatekeeper 弹窗 |
| G2 | U 盘拷入，`xattr -l` 确认无 quarantine | 双击即开 | 被拦（说明签名或架构有问题，而非 quarantine） |
| G3 | 下载后 `xattr -p com.apple.quarantine` 有值 | 首次拦 + 右键可开 + 二次不拦 | ①直接能开（说明 quarantine 被剥离，分发不安全）②右键也打不开（签名损坏）③每次打开都拦（未正确记录用户意图） |

**G3 的可复现构造方法**（无需真的上传网盘）：

```bash
# 骨架，不执行。给 .app 人为打上 quarantine 属性，模拟"从网上下载"
xattr -w com.apple.quarantine "0083;00000000;Safari;" OpenPicasa.app
xattr -p com.apple.quarantine OpenPicasa.app   # 校验
```

> 这个构造让 G3 可**重复、离线、无外部依赖**地测——不必每次真的下载。但**必须在至少一次真机下载场景里交叉验证**一次，因为真实 quarantine 值格式可能略有差异。

### 5B.3 TCC 授权测试（macOS 特有，Windows 上不存在）

macOS 的 TCC（Transparency, Consent, and Control）会在应用访问「图片/桌面/下载/文稿/外接盘」时弹框。**这不是可选项，是必须建模的流程**——否则会出现在开发机"能用"、在用户机器上"选了目录什么也读不到"的情况（因为用户点了"不允许"，而应用静默失败）。

| 用例 | 场景 | 预期 | 关键点 |
|---|---|---|---|
| TCC-01 | 首次选 `~/Pictures` | 系统弹"想要访问你的照片"→ 允许 → 正常索引 | 必须用 `NSOpenPanel` 触发；**自己拼路径遍历会静默失败** |
| TCC-02 | 首次选 `~/Desktop` / `~/Downloads` | 各自弹框，允许后正常 | 三个位置是**独立授权**，不能假设一次授权全覆盖 |
| TCC-03 | 选外接盘（`/Volumes/xxx`） | 弹"可移除卷"授权（或直接可读，取决于卷格式） | 需实测确认 |
| TCC-04 | **拒绝授权后的降级** | **明确提示"未获得访问权限，请在系统设置中开启"**，并给出跳转按钮；**不崩溃、不静默空列表** | 这是最容易被漏测的一条。空列表会被用户当成"软件坏图" |
| TCC-05 | 授权后**重启应用** | 授权仍然有效，无需重复授权 | TCC 记住的是 bundle-id + 签名，**ad-hoc 重签名后可能失效**，需实测 |
| TCC-06 | 在**系统设置→隐私与安全性**里手动撤销授权后重启应用 | 回到未授权状态，再次选目录时重新弹框或提示 | 撤销后应用**不得**读到已缓存路径 |
| TCC-07 | **重新构建导致签名变化**（ad-hoc 每次重签 CDHash 变） | 观察 TCC 授权是否失效 | **M1 处置见下方"TCC-07 处置决定"** |
| TCC-08 | 选中含**符号链接**到受保护目录的文件夹 | 不因链接绕过授权（系统应拦截） | 安全回归 |

> **TCC-07 是本项目特有的风险**：ad-hoc 签名每次构建 CDHash 都会变，可能导致开发期反复弹授权。这不是 bug，但会让团队误以为"TCC 不稳定"。**必须在文档里写明，否则会被当成缺陷反复排查。**

#### 5B.3.1 TCC-07 的 M1 处置决定（三选一，含推荐）

> **问题**：ad-hoc 签名每次构建 CDHash 都会变，TCC 授权可能随之失效。**这属于产品体验问题，并非纯技术风险**。

**三个候选方案对比**

| 方案 | 做法 | 优点 | 缺点 | 代价 |
|---|---|---|---|---|
| **(a) 接受重新授权** | 不改签名方式，每次构建后用户需重新授权目录 | 零工程成本 | 开发期每天都烦；**对最终用户是"更新版本后要重授权"** | 用户负担 + 支持成本 |
| **(b) 固定签名身份** | 用**自签根证书**（非 Apple 账号）建一个稳定 identity，`codesign --sign "PicasaTest"` 代替 `--sign -` | CDHash 变化不再导致 identity 变；一次配置长期有效；**不需要 Apple 开发者账号** | 需在每台测试机/CI 导入同一张自签证书；证书过期需重签 | 一次性配置成本（低） |
| **(c) security-scoped bookmark** | 用 bookmark 持久化访问权 | 沙盒下是标准做法 | **M1 不沙盒，bookmark 是多余的**；且引入 blob 存储与失效处理 | 复杂度高、收益低 |

**推荐：(b) 固定签名身份**

理由：
1. **(c) 不适用**——02 §7.6.2 已明确「非沙盒应用在用户经面板授权后，TCC 授权按路径持久化，不需要 bookmark」。为不需要的场景引入 bookmark 是给自己造复杂度。
2. **(a) 只是把问题推给用户**，且与 01 §11.5 的"装得上、打得开、走得通"（红线 R-3）气质冲突——如果每次更新都要重授权，那"走得通"的体验就是打折扣的。
3. **(b) 成本最低且根治**：自签证书不依赖 Apple 账号、不影响 ad-hoc 的本质（仍是本地签名、仍需右键绕过 Gatekeeper），**只把"每次构建都变的临时身份"换成"团队内稳定的身份"**。

**M1 落地要求**

| 项 | 要求 |
|---|---|
| 默认做法 | **M1 用 (b)**：生成一张团队自签证书，导入开发机与 CI，构建脚本固定用它 |
| 若 (b) 也失效 | 退回 **(a)**，并**必须**由 PM 写进安装指引（"更新版本后可能需重新授权一次目录访问"），同时在 UI 上给出明确的重新授权路径（复用 TCC 拒绝降级的提示与跳转按钮） |
| **禁止** | 只在测试文档标"风险"而不给结论。TCC-07 必须产出**二值结论**（失效/有效）+ 对应处置落地 |
| 结论未出时 | 该项为 `BLOCKED`，**不得默认通过** |

**测试动作**：(1) 用 (b) 构建两次，比对 CDHash 是否稳定；(2) 在稳定身份下验证授权跨重启保留；(3) 再故意改一次签名，验证"失效"路径的 UI 提示是否到位。

### 5B.5 Retina 与多显示器

| 用例 | 场景 | 预期 |

## 5C. 照片目录零写入（v2.0 核心命题，已升级）

> **命题变更**：v1.0 是「`.picasa.ini` 零写入」；v2.0 升级为「**照片目录零写入**」。
>
> **为什么这更好测**（这是减负的典型）：
> - 不用再关心 ini 的格式、BOM、换行、未知键、6 位浮点——**那些知识负担整个消失了**。
> - 断言范围从"一个文件"扩大到"整个目录树"，**更强**，但判据更简单：**目录里什么都不能变**。
> - 不需要解析任何格式就能判定，因此**判据没有争议空间**。
>
> **一句话**：断言越强、越好写，这是好事。

### 5C.1 零写入的精确断言（六种操作全覆盖）

**监控手段**：`fs_usage -w -f filesys`（实时系统调用）+ `fswatch -r`（目录级事件）双通道，互相校验。前者能看见 `open(O_WRONLY)`，后者能看见 `rename`/`unlink`。

> **⚠️ 监控对象 = 整个照片目录前缀，不是某个文件名**（v2.1 明确）。
> 过滤条件必须写成 `*/photos/**` 这样的**目录前缀**，而**不是** `.picasa.ini` 文件名。
> 原因：R-1 已从「ini 零写入」升级为「**照片目录零写入**」——现在任何文件（含我们自己的临时文件、锁文件、缓存）出现在该目录下都算违规。
> **如果过滤条件还是那个文件名，等于把 90% 的攻击面留在了监控之外。**

```bash
# 骨架，不执行。正确做法：按目录前缀过滤
sudo fs_usage -w -f filesys | grep -F "<照片目录绝对路径>"      # 目录前缀
fswatch -r --event-flags "<照片目录绝对路径>"                    # 递归目录
```

| 操作类别 | 系统调用 | 为什么必须断言 |
|---|---|---|
| **写入** | `write` / `open(O_WRONLY\|O_RDWR)` | 最基本的破坏 |
| **创建** | `create` / `mkdir` | 往用户目录塞 `.tmp`、`.bak`、锁文件、缓存 |
| **重命名** | `rename` | 原子写实现的典型动作，最容易漏 |
| **删除** | `unlink` / `rmdir` | 误删用户文件，最严重 |
| **改权限** | `chmod` / `chown` | 会破坏用户既有权限设定 |
| **改时间戳** | `utimes` / `setattrlist` | 即使内容没变，改 mtime 也是污染（会影响同步盘/备份工具） |

**全流程操作脚本**（每一步之间都要检查零写入）：

```
启动 → 添加目录 → 扫描 1 万张 → 滚动到底 → 切三档尺寸 → 搜索 →
进查看器 → 翻页 100 次 → 放大到 400% → 全屏 → 退出查看器 →
折叠左栏 → 切换文件夹 → 托盘操作 → 退出应用
```

**判定**：上述全流程结束后，照片目录树满足：
1. `find . -type f | sort` 结果**逐项相同**；
2. 每文件 `SHA-256` **全等**；
3. 每文件 `mtime` **全等**（这条最关键，见下）；
4. `fs_usage` / `fswatch` 日志中**照片目录路径下零条**上述六类操作。

> **为什么连 mtime 都要查**：只查哈希会漏掉"读进来无脑重写、字节碰巧一样"的实现。**mtime 不变才是"根本没有以写模式打开过"的分水岭。** 这条判据在 v1.0 就立住了，v2.0 继续保留。

### 5C.2 正向断言：偏好必须真的记住（**绝不可删**）

> 这是我在 v1.0 就提出、Lead 明确要求保留到底的陷阱：
> **如果应用"干脆什么都不记住"，那"目录零变化"这条一样能通过。** 零写入用例单独看是**不可证伪的**。

因此每条零写入用例都必须**同时**验证两件事：

| 方向 | 断言 |
|---|---|
| **负向** | 照片目录零变化（§5C.1 的六类操作全为零） |
| **正向** | 应用容器里**确实产生了预期的状态变化**：`preferences.json` 的 mtime 更新且内容包含刚改的值；`NSUserDefaults` 的 plist 被写入 |

**具体对照表**（操作 ↔ 应在应用容器产生什么）：

| 用户操作 | 应用容器必须发生 |
|---|---|
| 切三档缩略图尺寸 | `preferences.json` 中 `thumb_size` 更新 |
| 改窗口尺寸/位置 | `NSUserDefaults` 中 window frame 更新 |
| 折叠左栏 | `NSUserDefaults` 中折叠状态更新 |
| 切到另一个文件夹 | `NSUserDefaults` 中 last_dir 更新 |
| 滚动栅格 | 滚动位置更新（或明确声明不持久化——**那也要写在规格里**） |

> **判据**：负向与正向**同时成立**才算通过。任一侧单独成立 → 判失败。
> 这条在 v2.0 下比 v1.0 **更重要**：因为现在数据完全自立，"记不住"不再是"反正原版也没记全"，而是"这个程序有 bug"。

### 5C.3 反向用例：目录不可写必须照常工作

| 用例 | 预置 | 期望 |
|---|---|---|
| RO-R1 | `chmod -R a-w <照片目录>` 整个目录只读 | **正常打开、扫描、浏览、零报错** |
| RO-R2 | 目录只读 + 位于只读挂载点（DMG 内样本） | 同上 |
| RO-R3 | 目录属主为他人，当前用户只读 | 同上 |

## 5D. 自有数据模型的正确性（v2.0 新增测试面）

> 「做一个新程序」意味着**数据完全自立**：没有原版格式兜底，自家存储坏了就是真坏了。
> v1.0 的健壮性测试只有 5 条（INFRA），v2.0 需要独立成章。

### 5D.1 存储架构（测试假设，待 02 v3.0 校准）

| 数据 | 位置 | 可丢失性 |
|---|---|---|
| 图库索引（含缩略图 BLOB） | `~/Library/Application Support/<bundle-id>/index.sqlite` | **不可丢**（重建需重扫） |
| 缩略图缓存 | `~/Library/Caches/<bundle-id>/` | **可丢**（系统会清，必须能重建） |
| 偏好与 UI 状态 | `~/Library/Preferences/<bundle-id>.plist` + `Application Support/.../preferences.json` | 可丢（回默认值） |
| 日志 | `~/Library/Logs/<bundle-id>/` | 可丢 |

> **关键区分**：`Caches` 与 `Application Support` 的语义不同——**macOS 会在磁盘紧张时清 `Caches`，但不动 `Application Support`**。
> 把索引放错位置会导致"用户的图库突然空了"，是 M1 的 P0 级设计错误。测试要盯住这一点。

### 5D.2 缓存与索引的自愈

| 用例 | 预置 | 期望 | 优先级 |
|---|---|---|---|
| DM-01 | 删除整个 `~/Library/Caches/<bundle-id>/` | 应用**正常启动**，缩略图按需重建，不报错 | P0 |
| DM-02 | 删除 `index.sqlite`（索引） | 检测到缺失 → **自动重建**（重扫）+ 进度反馈；不崩溃 | P0 |
| DM-03 | `index.sqlite` 随机损坏 200 字节 | 检测到 → **备份坏库** → 自动重建；**不弹"数据损坏"吓用户**（或弹但可一键修复） | P0 |
| DM-04 | `index.sqlite` 被替换成 0 字节空文件 | 同 DM-03 | P0 |
| DM-05 | `index.sqlite` 被替换成**非 SQLite 文件**（如随机二进制） | 同 DM-03，不 panic | P0 |
| DM-06 | `index.sqlite` 权限被改为 000（不可读） | 明确提示"无法访问索引"，**不静默空图库** | P1 |
| DM-07 | 磁盘满时建索引 | 降级为"仅元数据"或明确提示，不崩溃、不产生半截库 | P1 |
| DM-08 | 建索引过程中 `kill -9` ×10 | 重启后续扫，无重复条目，DB 始终合法（WAL） | P0 |

### 5D.4 Schema 版本与升级（M1 只写用例，不实现）

> M1 只有 v1 schema，但**必须现在就把断言写下来**，否则加 schema 时会毫无约束。

| ~~批量编辑吞吐（F10-17）~~ | 100 张 ≤60s | — | — | — | `M2 恢复` |
| ~~导出吞吐（F10-18）~~ | 100 张 ≤90s | — | — | — | `M2 恢复` |
| ~~百万张（F10-20）~~ | 不崩溃可搜索 | — | — | — | `M2 恢复`（01 v2.0 已移出 M1 承诺） |

> **5s 是验收线，3s 是设计目标**（02 §10.2.1 明确）。若实测落在 3~5s，M1 仍通过；**超 5s 即 M1 不通过**，不接受"技术上紧张"为由放宽。

**红线定义**：**超过门禁值 ×1.5** 视为阻塞缺陷（Blocker）；门禁值 ×1.0~1.5 视为严重缺陷，进入发布评审。**目标值仅作优化参考，不判失败。**

**测量纪律（引 02 §8.1，测试侧强制执行）**：
1. 所有性能数字**必须标注设备**（基准机 = 本机 Apple Silicon / macOS 27.2），跨平台数字单独标。
2. **三次取中位数**，同时记录 min/max（抖动比均值更有信息量）。
3. 冷/热缓存分开；冷启动需重启后首次或 `purge` 近似（macOS 无法可靠清 OS 缓存）。
4. 报告中必须写明**图库规模、JPEG 占比、平均尺寸、磁盘类型**，否则结果不可复现、不可比。
5. 性能测试 M2 起进 nightly，**回归即告警**；人肉测一次不算数。
6. macOS 内存一律用 `footprint -p <pid>`，**禁用 `ps` 的 RSS**（会漏算压缩内存，导致"虚低通过"）。

#### 6.1.1 内存测量口径（v1.0 已按 02 v2.0 §2.6.2 修正）

> **v0.3~v0.4 的写法是错的，这里明确纠正**：旧版写"RSS + GPU 显存**合计** ≤700MB"，并声称"必须分列 RSS/GPU 合计判定"。
> 02 v2.0 §2.6.2 指出：**macOS 是 UMA 架构，`phys_footprint` 本身已包含 GPU 支撑分配**（IOSurface / Metal backing）。
> 因此**相加会重复计算**，得出偏高的假超标结论；而"只报合计"也是错的——**合计就是那一个数，不该有合计**。

| 项 | 正确口径 |
|---|---|
| **唯一权威数字** | **`footprint -p <pid>` 的 `phys_footprint`**（已含 GPU-backed allocations） |
| **判定** | `phys_footprint ≤ 700 MB`（10 万张，F10-19） |
| **禁止** | ❌ `RSS + GPU 相加`（UMA 下重复计数）　❌ 用 `ps` 的 RSS（漏算压缩内存与 GPU） |
| GPU 侧分析（仅排查用） | `MTLDevice::currentAllocatedSize` 作**参考值**，**不得**与 `phys_footprint` 相加；`vmmap` 看 `IOSurface`/`Metal` 区间 |
| 报告格式 | 必须写明 `method: "footprint"`、`phys_footprint_mb`，并附注 **"phys_footprint already includes GPU-backed allocations; do not add metal_allocated_mb"**（02 要求此警告写进脚本输出，防止后人加错） |
| 降级策略 | 10 万张下单屏缩略图长边 ≤ 512px（T0 档）属**合规实现**，不判缺陷；用户显式放大单张时恢复高分辨率 |
| 采样点 | 静置 10 min 后 + 滚动 5 min 后各测一次（02 §10.2.4） |

> **为什么这条值得单独立一小节**：v0.4 我按"更严"原则写了"合计"，看起来更保守，实际上**方法论错误**——UMA 下相加会把同一块内存算两遍，导致一个健康实现被判超标，团队为了"达标"去砍真实需要的缓存，反而伤性能。**量纲错比数值错更危险，因为它不报错。**

### 6.2 长稳与内存

- **2 小时连续操作**（滚动 + 打开 + 编辑 + 导出循环）：RSS 增长 < 5%，无句柄/FD 泄漏。
- **1000 次打开/关闭图片**：内存回到基线 ±10%，无 GPU 资源泄漏。
- 用平台工具采样：macOS `leaks` / Instruments，Linux `valgrind --leak-check=full` 或 heaptrack，Windows CRT 泄漏检测。

### 6.3 崩溃与断电后索引自愈

这是非功能测试里最容易被忽略、后果最严重的一组。

| 故障注入 | 手段 | 期望 |
|---|---|---|
| SQLite 文件损坏 | 随机翻转 DB 文件 200 字节 | 启动检测到 → 备份坏库 → 自动重建索引 → 不崩溃、不丢用户编辑（ini 为准） |
| 断电/强杀 | 建索引过程中 `kill -9`（Windows: TerminateProcess） | 重启后 DB 处于合法状态（WAL 生效），索引标记为"不完整"并续扫 |
| **编辑过程中强杀** | **编辑循环中 `kill -9` ×10 次**，每次重启后检查已保存指令 | **已保存编辑指令零丢失**、ini 始终合法完整（F10-21 / TC-NLE-010，是 OUT-05 原子写的端到端证据） |
| 索引与 FS 不一致 | 绕过应用外部删 500 张 / 改 50 张 mtime | 重扫后条目与磁盘一致，无幽灵条目 |
| 索引与 FS 不一致（增） | 外部新增 500 张 | 监视或重扫后出现，不重复 |
| 磁盘满 | 把缓存盘填满 | 建索引降级为"仅元数据"，明确提示，不崩溃 |
| 只读介质 | 图片在只读挂载点 | 可浏览、可查看；编辑操作给出明确提示而非静默失败 |
| 外接盘拔出 | 操作中卸载卷 | 无 panic，条目标记离线，重新挂载后恢复 |
| 时钟回拨 | 系统时间倒退 1 天 | 增量扫描不漏文件（不能只靠 mtime，需 size+hash 兜底） |

### 7.3 GUI 自动化方案

Picasa 的核心体验在 GUI，而 GUI 天生难测。策略是**把可测性设计进架构**（需与 dev 约定，属于测试对架构的输入）：

1. **视图模型/渲染分离**：`picasa-ui` 内把"状态 + 交互逻辑"抽成不依赖 GPU 的纯逻辑层（ViewModel），可用单元测试直接驱动；`egui` 的即时模式特性天然适合这种做法。
2. **交互用 Harness 驱动**：使用 egui 的测试 harness（`egui_kittest` 或自建 `Harness`），构造 `Context` + 注入事件（点击/键盘/滚动）+ 断言 `Response` 状态与 VM 状态，**不需要真实窗口**。
3. **截图回归**：harness 渲染到纹理 → 落 PNG → 与基准图比较。
   - 比较策略：**分区域**（把文本区域、动态时间戳区域遮罩），其余区域逐像素比较，差异像素占比 ≤ 0.1% 且无单块连通区域 > 64 px。
   - **基准图按平台/字体配置分目录**（§3.1 的 `golden/{platform}/`），因为字体抗锯齿不可跨平台一致。
   - 只在 CI 的固定环境生成基准，本地不更新基准（避免"本地基准污染"）。
4. **真实窗口 E2E**（少量、夜间跑）：macOS 用 AppleScript/`osascript` 或 `AXUIElement`、Windows 用 UIAutomation、Linux 用 `xdotool` + Xvfb。仅覆盖 §2.4 的 8 条旅程，且**允许 3% flaky 重试一次**。
5. **禁止**把 GUI 自动化当作主要回归手段——维护成本极高，优先把逻辑压到 VM 层测。

### 7.5 模糊测试（cargo-fuzz）

| fuzz target | 输入 | 目标 |
|---|---|---|
| `fuzz_ini_parse` | `.picasa.ini` 字节 | 无 panic / 无 OOM / 无超时；解析成功的输出可再序列化回等价 |
| `fuzz_ini_roundtrip` | ini 字节 | `parse → write → parse` 幂等（第二次 parse 结果与第一次等价） |
| `fuzz_exif_parse` | JPEG/TIFF 头部段 | 无 panic；越界读被捕获；偏移量校验 |
| `fuzz_iptc_parse` | IPTC IIM 块 | 同上 |
| `fuzz_jpeg_segments` | 完整 JPEG | 分段遍历不越界；遇到未知段安全跳过 |
| `fuzz_edit_dsl` | 编辑指令字节/结构化随机 | 求值不 panic；无效指令被拒绝而非误执行 |

- **语料**：初始 corpus 用 §3 全部样本 + 原版 ini 样本；每发现一个崩溃用例，最小化后**永久入库**作为回归语料。
- **字典**：`[Picasa]`、`[Contacts]`、`name=`、`category=`、`star=yes`、`caption=`、`keywords=`、`crop64=1,`、`rect64(`、`filters=`、`enhance=1`、`autolight=1`、`sepia=1`、`sat=1,`、`tilt=`，以及 EXIF `0xFFE1` 标记等（**按 §5.1 的真实键名构造，不要喂虚构字段**）。
- **达标标准**：每个 target 累计 ≥ 24 CPU 小时无崩溃，且覆盖率增速进入平台期（`cargo fuzz coverage` 观察）。发现崩溃 → 修复 → 跑满再验收。
- 建议同时在 fuzz 构建下启用 ASAN/UBSAN（`-Zsanitizer=address`），把"未崩溃但越界"也抓出来。

### 8.1 大规模图库生成

原则：**不复制 100 万张真实图**（磁盘/时间不可承受），用三类技巧：

1. **硬链接/符号链接放大**：生成 1000 张基础图 → 建 1,000,000 个硬链接。注意这会考验"去重"逻辑（同一 inode 不应重复入索引），是特性也是陷阱，需单独用例。
2. **稀疏/极小文件**：损坏样本用 0 字节与截断文件批量生成，压测错误路径。
3. **确定种子**：图库结构用固定 PRNG seed，保证可复现。

## 9. 缺陷分级与准出

| 级别 | 定义 | 举例 | 准出要求 |
|---|---|---|---|
| **P0 Blocker** | 数据丢失/损坏、崩溃、无法启动 | 编辑破坏原图、ini 写坏导致原版读不出、启动 panic | 0 个 |

- P0 = 0，P1 = 0。
- 兼容性用例（INI-*、OUT-*、RT-*、COMPAT 组）**全绿**，不允许豁免。
- 覆盖率达标（§10）。
- 性能红线内（§6.1）。
- 连续 3 次 CI 全绿（含 fuzz 无新增崩溃），排除 flaky。

## 10. 质量门禁与里程碑 DoD

### 10.1 通用门禁（所有里程碑生效）

| 门禁 | 阈值 | 工具 | 阻断 |
|---|---|---|---|
| 编译 | 所有 target/feature 组合通过 | `cargo check --all-targets --all-features` | 是 |
| 格式 | 0 diff | `cargo fmt --check` | 是 |
| Lint | 0 warning | `cargo clippy -- -D warnings` | 是 |
| 单测行覆盖率 | 全 workspace ≥ **75%** | `cargo llvm-cov` | 是 |
| 核心模块行覆盖 | `picasa-ini` / `picasa-imaging` / `picasa-core` ≥ **85%** | `cargo llvm-cov -p ...` | 是 |
| ini 解析器覆盖 | 行 ≥ **95%**、分支 ≥ **90%** | 同上 | 是 |
| 关键模块变异测试 | 变异杀伤率 ≥ **70%**（ini 解析器 ≥ 80%） | `cargo mutants`（nightly） | 是（里程碑） |
| 文档测试 | 全通过，公开 API 均有示例 | `cargo test --doc` | 是 |
| 依赖安全/许可 | 无 high/critical 漏洞，许可证白名单 | `cargo deny check` | 是 |
| 性能回归 | 对比 main 基线不劣化 > 10% | criterion | 是（PR 报警） |
| fuzz | 无新增崩溃语料 | cargo-fuzz | 是 |

> 覆盖率不是目的：**新增代码的增量覆盖率（diff coverage）要求 ≥ 85%**，比总量更有效。可用 `cargo llvm-cov --fail-under-lines 85` 并对 diff 生效。

### 10.2 里程碑 DoD（已与 01 §11 对齐）

> **v0.2 已按 `01-产品功能清单.md` §11 的真实 M1/M2/M3 功能点范围重写。**

### 10.4 A/B/C 证据分级与「BLOCKED-待原版样本」标记（对齐 01 §0.6）

01 §0.6 把 25 项效果按证据强度分为 A（10 项，有公开逆向 id）/ B（1 项 F3-25 渐晕，id 待定）/ C（14 项，无任何证据）。**这直接改变测试的优先级判定方式**——不能再用统一 P0 门禁去压所有效果。

| 等级 | 项数 | 功能点 | 测试处理 | 门禁地位 |
|---|---|---|---|---|
| **A 级** | 10 | F3-19~F3-24、F3-26~F3-29 | 正常对拍，TC-EDIT-007 | **可作 P0 门禁**（有 id 证据，dev 无需自造） |
| **B 级** | 1 | **F3-25 渐晕**（P0，且在 M1 清单内） | 标记 `BLOCKED-待原版样本`，TC-EDIT-020 | **取证前不计入通过率**；取证失败则 M1 范围需调整（PM 将与 Lead 确认） |
| **C 级** | 14 | F3-30~F3-43 | 标记 `BLOCKED-待原版样本`，TC-EDIT-020 | **M2 结束前不计入通过率** |

**「BLOCKED-待原版样本」的确切含义（三条，避免被滥用）**：

1. **不是"跳过测试"**，而是"**该用例尚不具备可判定的基准**"。它必须在测试报告中以独立区块出现，写明"证据待补"，**不得计入分母、也不得计入分子**——既不能拖死通过率，也不能注水。
2. **取证完成即解除**：拿到原版 ini 样本并确定真实 filter id / 参数个数 / 取值范围后，状态从 `BLOCKED` 转为 `ACTIVE`，正式纳入门禁。取证失败的项，按 01 §0.6 规则 4 走 §12 登记为**有意差异**，并在 UI 明示"该效果与原版不保证一致"。
3. **绝对禁止**以"自造私有 ini id"的方式让用例"通过"。这是 01 §0.6 规则 1 的红线：自造 id 会让原版打开时显示原图，等于承认我方写的数据原版读不懂，与 1:1 承诺直接冲突。**测试侧发现私有 id 写盘，直接判 P0 缺陷，不论像素对拍多好。**

> 这条设计的价值：C 级效果的像素对拍如果硬写成 P0 门禁，**唯一能满足它的路径就是让 dev 自造私有 id**——那是把我们最想避免的失败模式，用测试逼出来。声明为 BLOCKED 才是正确的工程姿态。

**报告呈现要求**：测试报告必须同时给出两个数字——
- **计入 BLOCKED 的通过率**（用于里程碑内部质量趋势）；
- **排除 BLOCKED 的通过率**（用于对外承诺与 DoD 判定）。
只给一个数字必然产生歧义。

> **本组最容易放过的一条**：`TC-M21-PERF-001`。它的失败形态是「测试全绿、跑分也还行，但索引根本没用上」——
> `ORDER BY COALESCE(...)` 这个表达式让 `idx_photos_folder_taken` 失效，5 万张首页从 1.77 ms 退化到 199 ms，
> 而 python 直连同一条 SQL 却走索引，差异只在「生成列探测用的是 `table_info` 还是 `table_xinfo`」。
