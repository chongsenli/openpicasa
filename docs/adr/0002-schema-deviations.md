# ADR-0002：schema v1 与设计文档的两处有意偏差

- 状态：已采纳
- 日期：2026-10-29
- 相关：02 技术架构 §5.3（schema）、`crates/picasa-db/src/schema.rs`

## 背景

02 文档的 §5.3 给出了 v1 建表语句，其中包含两张表：一张 `photos_fts`（FTS5 全文索引），
以及 `photos` 表上的若干「为将来预留」的冗余列。落到实现时，这两处都会产生实际问题。

## 决定

### 偏差一：不建 `photos_fts`

文档原意是让搜索走 FTS5。但 FTS5 默认分词器 `unicode61` **不切分中文**——
它按空白与标点切词，`苏州行` 这样的连续汉字会被当成一个 token，搜「苏州」命中不了。
要用必须挂 `simple` 分词器或 `jieba` 扩展，前者对中文等于不分词，后者要引入 C 依赖并
在每个平台的 SQLite 里注册虚表，与 `rusqlite bundled` 的静态链接方式冲突。

同时，FTS5 是外部内容表（`content='photos'`），删除或改名时需要旧值来喂 `'delete'` 命令，
而我们的删除路径是「按 folder 批量删」，拿不到逐行的旧值，得额外查一遍。

M1 的搜索规模是「单库万级照片、用户输入一个子串」，`LIKE '%x%' ESCAPE '\'` 配合
`name_key`（NFC 归一化 + 小写）在这个量级上是毫秒级，完全够用。

**决定**：M1 不建 FTS5，搜索走 `LIKE` + `name_key`。`escape_like()` 负责转义
`%` / `_` / `\`，保证用户搜 `100%` 不会退化成通配。等 M2 有真实中文分词需求时，
再评估「引入 jieba 并自建 token 表」而不是 FTS5。

### 偏差二：不加「预留」冗余列

凡是 M1 代码里没有任何读写路径的列，一律不建。理由是 SQLite 加列虽然便宜
（`ALTER TABLE ADD COLUMN` 常数时间），但**删列要重建表**；而在没有任何数据依赖时，
加列的成本比删列低一个数量级。M1 先窄，M2 再宽。

留下的列都有明确的读写方：
| 列 | 谁写 | 谁读 |
|---|---|---|
| `photos.taken_at_src` | 扫描器（EXIF / mtime / 文件名推断） | 排序与分组 |
| `photos.orientation` | EXIF 探测 | 缩略图与查看器解码 |
| `photos.thumb_state` | 缩略图生成器 | 增量补图队列 |
| `photos.decoder_ver` | 解码器常量 | 缓存失效判定 |
| `thumbs.data` | 缩略图生成器 | 栅格与查看器 |

## 后果

- 搜索能力弱于「真正的全文检索」：不支持词干、不支持相关度排序。M1 的验收标准只要求
  「按文件名子串能筛出结果」，满足。
- 迁移路径清晰：`schema_migrations` 表记录已应用版本，M2 加 FTS 或加列时写 v2 迁移即可，
  已有库不需要重建。
- 两处偏差都写在 `schema.rs` 的文档注释里，避免后来者以为漏写。
